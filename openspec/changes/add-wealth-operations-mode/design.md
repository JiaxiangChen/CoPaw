## Context

财富工作台使用 iframe 登录上下文；角色在 store 初始化时解析，但规划 API、场景和分发机构各自读取上下文。规划使用外部 Java 服务，本次用户明确只改前端，Java 由其同事确认。机构常量在此仓库省略了完整分行名单，不补造名单。

## Goals / Non-Goals

**Goals:** 白名单 V00001/80008888 的跨分行中台代建；普通模式请求与原行为不变；状态及异步结果隔离；明确前端和服务端责任。

**Non-Goals:** 不改 Python、Java、共享登录态或父页面消息协议；不扩展总行操作、岗位选择或他人规划写权限。

## Decisions

- 白名单由 `console/public/env-grey-control.js` 的 `operationsUsersByBranch` 按分行配置，默认示例为 V00001/80008888；运行时读取，不在 bundle 保留默认名单。配置缺失或格式错误时拒绝开放，不支持通配符。配置修改后重新加载页面生效，无需构建；不承诺页面内热更新。
- 运维上下文独立存于工作台内存，白名单联合检查真实分行和用户编号，不持久化。业务上下文仅覆盖目标分行、机构根和中台岗位；姓名、用户编号、渠道、系统、鉴权头保留真实身份。关闭时原样返回 iframe 上下文，避免影响其他页面。
- 开启后先选择分行，选项直接读取 BBK_ID_MAP 排除 100。未选分行时展示明确提示，不发业务请求。hideLogo=true 禁用运维；离开工作台或身份改变时清理运维状态。
- 切换前有草稿、编辑对象或分发选择时确认丢弃，写请求期间禁止切换；切换后重挂载业务页面并重置列表、人员、场景和任务数据。请求使用上下文代次拦截迟到响应。普通草稿缓存保持原样，运维草稿不写入普通角色缓存。
- 复用现有 GET/POST/PUT/DELETE 规划和分发接口。运维 GET/POST/PUT 的 role=middle、bbkId=目标分行，sapId 保持真实操作人，POST/PUT 的 bbkOrgId 使用所选分行根；DELETE 在原 sapId 基础上补 role/bbkId。不引入新接口或伪造 Cookie。
- 规划可见范围沿用中台以保留原冲突校验数据；写操作必须有服务端明确的 editable=true。不以本地临时创建记录推断归属，刷新后继续以 Java 授权为准。
- 机构树根沿用当前中台查询的 orgLvl/sysId 契约，编码替换为目标分行；下级机构继续使用服务返回的 mOrgCode/mOrgLvl。Java/机构服务对接方需确认测试分行 orgLvl 适用于分行根。

## Risks / Trade-offs

- [前端白名单不是授权] → 文档明确 Java 必须基于可信登录态校验 V00001/80008888、目标分行及本人代建权限；未经 Java 联调不声称跨分行生产可用。
- [editable 缺失或错误可能扩大写权限] → 运维写入口及 store 仅接受显式 true；真正归属必须由 Java 校验。
- [真实身份请求头与目标分行参数不同] → 保留真实身份用于授权和审计，明确目标分行为业务作用域；由服务端确认，不修改全局身份构造器。
- [目标内核不可用] → 采用 Chromium 108 支持的标准控件与 CSS，记录真实浏览器验证范围，不用 UA 伪装兼容验证。
