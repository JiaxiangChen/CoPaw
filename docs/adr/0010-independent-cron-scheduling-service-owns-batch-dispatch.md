# Independent Cron Scheduling Service Owns Batch Dispatch

Batch-managed scheduled work must be dispatched by an independent scheduling service, not by a SWE background dispatch worker and not by the legacy external scheduler callback. The scheduling service owns durable intent claiming, retry, dispatch telemetry, immediate refill after completed work, and periodic worker-capacity decisions. SWE remains the execution owner and is invoked only through the existing internal cron callback.

The callback contract now has an explicit **Dispatch Callback Source**. Batch-managed parent or child jobs skip legacy external scheduler callbacks when the source marker is absent. A scheduling-service request carries `callback_source=dispatch_service`, `dispatch_intent_id`, `dispatch_batch_id`, and `dispatch_attempt`; SWE then starts the job with `CronManager.run_job(..., is_manual=False)` and writes those identifiers into execution metadata. SWE sends its Agent execution result to Scheduler, which validates the dispatch identity before persisting the execution record. Receipt acceptance does not complete the dispatch intent. Scheduler's dispatch loop reads that record together with Monitor's subtask result and refills available capacity after settling the combined outcome.

Dispatching and worker-capacity adjustment are separate loops. `dispatch_ready_once()` claims and hands off due work without changing capacity. `adjust_worker_capacity_if_due()` runs only after the configured interval and uses recently completed intent outcomes to increase, decrease, or hold effective workers. This avoids coupling every dispatch with a capacity recalculation while still allowing a completed task to trigger the next dispatch immediately.

The first implementation keeps the existing cron definition and external scheduler infrastructure for non-batch jobs. Future work should move all due-time calculation, ordinary scheduled-job dispatch, and external scheduler replacement into the scheduling service, but that migration is intentionally out of scope for this change.

## Implementation Notes

The top-level `scheduler` service starts the scheduling loop from its own FastAPI lifespan when `SWE_CRON_DISPATCH_INTENTS_ENABLED` is enabled and the database is configured. Monitor does not host this loop. Parent batches are created through the physical timer callback. Each dispatch tick reconciles persisted execution results, recovers remaining stale intents, and dispatches available work; capacity adjustment runs independently. Legacy external callbacks to SWE for batch-managed jobs still return a skipped response.

`dispatched` is a handoff state, not a terminal state. It remains occupied while the Agent or its subtasks have not produced a final result. The scheduling service keeps a reclaimable lock timestamp and uses the existing `SCHEDULER_CRON_DISPATCHED_STALE_SECONDS` budget (default 7800 seconds) for Agent execution and subtask waiting together. Receiving the Agent result does not restart that clock. Current-attempt terminal results are excluded from stale recovery and fallback claiming so a bounded scan can finish them on its next tick. An Agent-success record still waiting for its subtask result uses the error `获取子任务状态超时` when recovered; missing Agent records keep their existing error and retry policy.

Callback transport outcomes are classified by whether Scheduler can know that SWE rejected the handoff. Connection establishment failures and explicit non-success HTTP responses remain retryable failures. Response-time transport failures such as read timeouts, interrupted reads or writes, and protocol termination are ambiguous because SWE may already have accepted the work; Scheduler records `callback_outcome_unknown`, keeps the intent in `dispatched`, and waits for execution feedback or stale recovery instead of immediately duplicating the run.

`due_at` is an eligibility boundary, not a dispatch priority. An intent must still satisfy `due_at <= now` before it can be claimed, preserving retry backoff. Once eligible, candidate batches, intents within a batch, and the claimed rows handed to SWE are ordered only by `dispatch_order` and `id`, so a retry resumes the batch's stable business order rather than being deprioritized by its later retry timestamp.

Dispatch-service callbacks must carry a valid positive `dispatch_intent_id`, a non-empty `dispatch_batch_id`, and a positive `dispatch_attempt`. Scheduler validates execution feedback against intent id, batch id, attempt count, job id, tenant id, and source id before updating the durable intent row. Scheduler also checks for an existing execution row by `(dispatch_intent_id, dispatch_batch_id, dispatch_attempt)` before inserting, so SWE retrying the feedback request does not duplicate execution history.

## Persisted Agent and subtask results

Scheduler and Monitor must access the same `swe_cron_executions` data. SWE continues to own `status`, and Monitor continues to own `async_status`; neither service's local behavior changes. No new feedback API, waiting state, database column, or Monitor polling worker is introduced.

The dispatch loop runs a bounded scan before stale recovery and the capacity gate, even when all worker slots are occupied. It joins active intents to executions by intent id, batch id, current attempt, job id, and tenant id. Both statuses must be `success` to complete. An Agent failure or Agent success with `async_status='error'` follows the existing retry limit and backoff; the latter records `子任务执行失败`. The canonical expired Cron-auth failure is terminal on its first attempt, records an explicit `鉴权过期` error, and is excluded from worker-capacity failure feedback because retrying or shrinking model capacity cannot repair the credential. Missing or unfinished results keep the intent dispatched. Completion and retry timestamps use the time the scan observes the final outcome, not the earlier Agent end time. Conditional intent updates retain the attempt and active-state guards, so repeated scans and late prior-attempt results cannot finish a new retry.

This decision deliberately adopts Monitor's existing aggregation rules, including its no-subtasks success case and waiting for pending subtasks before publishing an aggregate failure. Deployment must verify the shared database configuration and the existing Monitor status synchronization; the Scheduler change does not create those data producers.
