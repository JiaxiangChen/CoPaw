# 定时执行凭据先镜像到数据库，过渡期继续读取文件

为后续将定时执行凭据迁移到数据库，先新增数据库表并镜像现有 `cron_auth.json` 的全部状态变更，包括清理删除。过渡期所有现有业务读取仍以文件为准；文件操作成功而数据库同步失败时，原操作仍成功，不因数据库故障中断现有授权或任务执行。这接受暂时的文件与数据库差异，不承诺跨存储原子提交。

提供可重复执行的存量回填和核对工具，覆盖未发生新写入的既有凭据。未来切换到数据库读取属于后续阶段，本决策不代表已经允许切换。以上选择由用户于 2026-10-29 确认。

数据库同步失败只记录失败，由运维主动运行可重复执行的回填与核对工具补齐；本阶段不增加自动重试队列。工具通过内部 HTTP 接口提供，采用预览、回填、核对的操作方式，并支持按租户和来源筛选。

全量工具采用一次提交、后台自动分批执行的方式，通过任务 ID 查询进度，复用现有异步任务进度能力。进程中断后可重新提交并安全重跑，本阶段不增加跨实例自动接管。

用户随后明确不增加锁，依靠后续同步逐步收敛；这一最新决定替代此前要求作用域内统一排序的方案。用户接受过渡期存在差异，不承诺并发写入顺序或自动最终一致。回填与核对均由运维主动执行，系统不自动发起对账或修复；未来切库前的全量核对也由运维负责。

现有显式文件删除入口为 `POST /auth/cron-auth/cleanup`：调用 `cleanup_cron_auth_except_source()` 清理作用域下的 `.secret/cron_auth.json`，支持按保留来源、强制删除租户与 dry-run 控制。此入口属于同步删除的接入范围。

正常清理在文件删除成功后同步硬删除对应数据库记录。数据库删除失败仍遵循不阻断原操作的原则。运维核对发现“数据库有、文件没有”的记录时只报告，不自动删除；由运维确认后显式执行指定范围的数据库清理。普通回填不删除这类记录。

用户最终确认 `user_info` 沿用完整对象序列化为 JSON 文本、存入 LONGTEXT 的方案，其余顶层状态字段独立存列。这样保留未知字段及嵌套结构，不必依赖仓库中缺失的生产字段契约；此前关于将 `user_info` 内部展开为固定列的讨论不再作为实现要求。

工具协议与表结构见已确认的[详细设计](../superpowers/specs/2026-10-29-cron-auth-database-mirror-design.md)。未来读取切换仍属于独立阶段，不因本次数据库镜像及运维工具交付而自动发生。
