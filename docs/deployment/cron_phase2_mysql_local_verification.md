# 第二阶段本地 MySQL 8.1 验证记录

本记录补充此前仅SQLite/ASGI验证的缺口。使用Windows本地已有MySQL 8.1.0程序启动独立临时实例；不是业务库或预发布实例，也没有借用应用默认连接。三服务真实网关、平台与多实例文件路由仍未验收。

## 隔离边界

- mysqld使用`--no-defaults`，全新output/copaw-cron-mysql随机目录；只绑定127.0.0.1的独立空闲端口，关闭MySQL X端口，不注册Windows服务。
- 连接前核对`@@datadir`等于本轮创建的数据目录、server_id为本轮指定值。测试库名为test_cron_managed_随机后缀；升级验证使用另一个同实例隔离库。
- 不读取或修改D:/Mysql下的用户数据目录、现有配置或服务。只在明确拥有的临时库执行DDL/测试，未连接业务数据库；应用启动仍不加载本次人工SQL。
- MySQL测试只清理fixture的随机tenant/source和自己模型池的记录；验证后已核对进程身份并通过mysqladmin正常关闭，PID已退出。临时目录递归清理被工具安全策略拒绝，未改用其他方法绕过；目录保留在output/copaw-cron-mysql-7677b115be89449093937d6f1978a489，并通过本地.git/info/exclude精确排除，不提交/打包数据库文件或临时生成的证书。

## 旧草案升级材料验证

在第二个独立空测试库中先建完整表，再仅对该空库模拟早期草案：移除settled三列/两索引、移除queue_invalidation_version，并把三项状态时间降为秒精度。执行`cron_phase2_manual_upgrade.sql`的9条实际ALTER均成功。

之后再次运行18表核对：缺列0，新协议时间精度全部6，18表均InnoDB，两个收敛索引恢复。该结果只证明这些明确差异语句在MySQL 8.1及空草案上的语法/结构效果；不证明非空历史执行的模型、入队顺序、水位回填安全。业务库实际缺失其他字段时仍需真实SHOW CREATE TABLE和脱敏记录，不能直接套用猜测回填。

## 持久测试与真实场景

代码：`tests/integrated/scheduler/test_managed_cron_mysql.py`。

本地显式隔离配置下10项全部通过：4项配置保护和6项实际MySQL场景。

| 实际场景 | 证明的行为 |
| --- | --- |
| 并发创建同请求 | 共享任务/操作ID，只有一个定义及一次平台注册调用；平台为明确边界替身。 |
| 两表事务回滚 | Scheduler事务同时更新定义与状态后注入失败，SWE另一连接看到两者均未提交。 |
| SWE受理与结果 | Scheduler登记和派发，SWE真实连接按租约受理、并发开始只有一个赢家，重复完成只有一条旧历史。 |
| 分发/三态/回调/队列 | 实际分发和模式表写入；批回执重放去重；改普通后已入队的三条批工作仍可被查询领取。 |
| legacy与新任务同库 | 真正MigrationRepository导入两表快照，重复导入不变；新查询不暴露legacy，导入不能覆盖scheduler归属。 |
| 模型池并发与异步收敛 | 先验证旧intent占位阻止新领取；强制两事务进入同一scope锁竞争，容量1只有一个赢家；主success未settled继续占位，注入Monitor终态后由真实收敛器释放，等待执行才能领取。 |

资源准备、外部平台和Monitor最终异步事实在这些场景中是明确替身，真实Agent/Workflow业务服务未调用。MySQL行锁、事务、查询、唯一约束和跨连接可见性是真实执行的；不再仅由SQLite行为推断。

## 仍未证明的事项

- 实际目标MySQL版本/存量字段和数据、规模下的执行计划及锁等待。
- 外部平台时区、稳定触发字段、jobParam与真实Header透传。2026-10-17已按用户决定取消注册查回依赖：未保存ID视为注册失败，原操作重试可以新增，可能遗留重复定时器；本记录的数据库实测不证明消除了该外部风险。
- 真实SWE多实例的工作区、会话、报告产物可达性及完整业务执行/通知链。

因此本地MySQL通过不改变第二阶段整体尚需预发布验收的结论。开发侧可显式配置隔离测试库重复运行；行内调用方继续使用Postman流程，不要求运行Python。
