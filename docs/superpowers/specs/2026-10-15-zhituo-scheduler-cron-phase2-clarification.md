# 第二阶段完整澄清清单

日期：2026-10-15。状态：进行中，只细化设计，不开发业务代码。当前范围以[第二阶段边界](2026-10-15-zhituo-scheduler-cron-phase2-boundaries.md)为准。用户最新要求将剩余问题集中提出，因此本轮改为集中确认；已解决问题和源码可确定的实现事实不重复询问。

## 已确认、不重复询问

- SWE、Scheduler、Monitor 共库；Scheduler 管理定义和管理状态，SWE 写实际执行状态及结果。
- Scheduler 创建的任务及子任务不补写 jobs.json 或 SWE 旧内存；普通、批调度均走新入口。存量及第一阶段 legacy 快照不自动接管。
- 新管理页与旧页分开；Chat 双列表合并，旧在前、新在后；操作及结果预览标记已读按归属分流，不通过写接口失败回退探测归属。
- 分发异步、0～1000 人，散列在分发接口；三态切换只控制新触发，已入队及执行中的任务继续；单任务删除阻止未开始执行，已开始可完成。
- 更新期间暂缓新触发，已入队、运行中的任务按原快照继续；准备与平台同步确认完成后新版本才生效。期间被暂缓受理的触发不补跑，记录原因，之后等待生效排程的下一次正常触发。
- 增补能力已纳入：独立单任务启停、手动执行、批调度优先级、子任务批量操作、列表展示视图、标记已读和管理进度/安全重试。
- C1.1 已确认：单独停用任务时跳过尚未开始的排队执行，已开始的继续完成，其他任务不受影响；不套用整组三态切换的已入队继续规则。
- C1.2 已确认：恢复时将当时已有未读结果标为已读，保留历史内容；之后新产生的结果继续计为未读，不因迟到恢复处理被清除。
- C2.1 已确认：停用任务不接受手动立即执行，必须先恢复；新接口明确返回未受理原因，不在实际未执行时提示已开始。
- C2.2 已确认：任务有执行正在运行时，前端禁用再次手动触发，后端也拒绝新的手动触发，不为该点击追加排队执行，原执行不受影响；不借此取消任务原有自动执行并发配置。
- C2.3 已确认：同一任务已有受理但尚未开始的手动请求时，再次点击不新增执行，返回已有待执行请求及其进度；同一次请求重试同样复用原执行记录。
- C3.2 已确认：创建、更新采用同步主流程，等待必要准备和平台同步完成后返回；异常保留可查询进度与同次操作身份。分发保持异步，执行请求仍区分受理与运行完成。
- C3.3 已确认：用户直接调用的创建、更新失败后采用人工续办，复用原操作和已落库任务，从未完成阶段继续，不新增后台自动业务续办；平台结果不明先核对，不盲目重复注册。
- C3.4 已确认：没有未删除子任务且没有分发进行中时允许修改源任务内容；停用但未删除的子任务仍算存在。启停、三态和优先级是独立管理操作。
- C3.5 已确认：逻辑删除后的平台停用或 SWE 资源清理失败采用人工重试，保留“已删除、清理未完成”的可查可重试记录；不恢复任务，不新增自动后台失败续办。
- C4.1 已确认：明确的新一轮分发可以为曾删除子任务的接收方创建新 ID 的子任务，旧记录保持已删除，新旧资源及清理隔离；旧分发重试或迟到工作不得复活任务或另建替代任务。
- C4.2/C4.4 最新约定：分发失败由人工选择接收方发起新一轮分发重试，不单独开发旧轮续办接口；不新增后台自动业务失败重试。新轮使用当前源定义及本轮散列参数，复用未删除子任务和已有资源，不因旧轮失败重复建任务。服务重启后的原轮进度恢复仍需支持。
- C4.3 已确认：同一完整源任务身份一次只允许一轮分发排队或处理中，另一轮新请求不受理并返回当前进度；同次请求重复提交仍复用原分发。
- C4.5～C4.10 已确认：沿用均匀提前散列和 0～24 小时窗口；Cron 无法安全平移则按旧逻辑回退原排程并告警；0 人仅调整全部未删除子任务的散列排程；再次分发按源定义覆盖内容但保留子任务自身身份、启停及运行事实；模型缺失回退默认并告警，必要 Workflow/技能配置缺失则目标失败；分发进行中拒绝删除源任务。
- C5.1 最新确认：三态切换的外部处理失败只提示并支持人工重试，保留目标及逐项进度，不自动回滚、不新增自动业务失败续办；不能仅因外部同步未完成或失败而阻止整组触发。实际停用、删除、暂停批调度及其他独立业务校验仍有效，已有队列和运行继续。
- 新旧隔离已再次明确：本次设计约束新增接口和 Scheduler 管理的新任务通道；存量管理、执行及平台接口行为不变。公共代码复用也不得隐式改变老接口行为。
- R1、R2、R4、R5、R7 已确认按建议：三态切换允许逐对象临时混合且异步处理；源管理者管理关联任务，接收方仅管理自己；实际运行失败不自动重跑；只恢复已受理队列，不主动补生停机期间未收到的触发。R3 按用户修正：切换未完成不得改成另一个目标模式，可重试原切换。R6 按用户再次明确的共库原则整理：SWE 直接写执行状态和结果，Scheduler 读表，不等待执行完成回执；受理去重和异常恢复作为技术契约细化，不把人工核对功能当作已批准需求。

## 已解决 C1.1：单任务停用与排队执行

用户选择 1：跳过指定任务尚未开始的排队执行；已经开始的执行继续完成，其他子任务不受影响。

## 已解决 C1.2：恢复同时标记已有结果为已读

用户选择 1：沿用现有恢复行为，恢复同时将当时已有的未读结果标记为已读，保留历史内容；之后新产生的结果仍正常计为未读。实现时按一致的已读边界协调并发完成事件，不能无条件覆盖新结果。

恢复任务自身不能解除更新未完成、删除或整组调度模式等独立门禁；标记已读本身仍不会隐式恢复任务。

## 已解决 C2.1：停用任务不允许手动立即执行

用户选择 1：停用时不允许立即执行，先恢复再手动执行；新接口明确返回未受理原因，不沿用旧接口在未执行时仍可能返回 started 的含糊响应。

## 已解决 C2.2：运行中不接受新的手动执行

用户选择 1：指定任务已有执行正在运行时，不再接受新的一次手动触发，不为该点击新增排队执行，原执行继续完成。前端和服务端同时执行此规则；本条限制新的手动受理，不改变自动执行的既有并发配置。

## 已解决 C2.3：待执行的手动请求不重复受理

用户选择 1：某次手动请求已受理但尚未开始时，再次点击不新增执行，提示已有待执行请求并返回其进度。返回信息应准确表达已有请求及其定义版本，不虚报新请求已经开始。本规则不把未来计划执行的批意图当作已有手动请求。

同一次请求因超时等原因重试属于幂等恢复，必须复用同一执行记录，不因此次产品选择生成重复执行；不等同于用户发起一个新的手动请求。

## 已解决 C3.1：更新期间被暂缓的触发不补跑

用户选择 1：更新期间到达并被暂缓受理的调度触发不补跑，记录本次未受理原因。更新完成后等待生效排程的下一次正常触发；更新前已入队或已开始的执行继续完成。

同一个已记录跳过的触发，后续平台重试仍返回其原处理事实，不能在更新完成后变成一次补跑或新的执行。

## 已解决 C3.2：创建与更新同步处理

用户选择 1：创建、更新同步处理，等待必要的 SWE 准备和平台同步完成后返回；失败或超时保存可查询进度，重试复用同次操作和任务，不重复创建。分发保持异步；手动或自动执行的受理响应不等待 Agent/Workflow 等实际运行完成。

同步请求不表示数据库和外部系统存在统一事务，也不允许把 HTTP 超时当作任务未创建后重新分配身份。只有必要步骤确认完成才返回创建/更新完成；未完成时明确返回事实和可用标识，不能把受理当成功。

## 已解决 C3.3：创建与更新失败后人工续办

用户选择 1：用户查看失败原因后人工重试，复用原操作及已落库任务，从未完成阶段继续，不新增自动后台业务续办。不得重新分配任务或重复创建已完成的资源；同次操作不允许用不同内容覆盖。

本条不改变分发后台及执行派发的重试策略，也不排除同一请求内满足幂等条件的有界技术重试。

结果不明的平台注册必须先核对是否已经产生外部定时器，并沿用已存在绑定；无法确认时明确保持待核对状态，不能借人工点击重试盲目再次注册。具体核对能力需结合平台接口细化。

## 已解决 C3.4：无未删除子任务且分发结束后允许修改源内容

用户选择 1：源任务没有未删除子任务且没有分发进行中时允许修改内容；停用但未删除的子任务仍算存在。子任务全部逻辑删除后不因历史分发记录永久锁定源内容。独立启停、三态和优先级操作不受此内容编辑限制。

## 已解决 C3.5：逻辑删除后清理失败人工续办

用户选择 1：数据库逻辑删除不撤销。平台停用或 SWE 资源清理失败时，显示并保留“已删除、清理未完成”的记录，允许授权用户人工重试未完成步骤；不恢复任务，不新增自动后台失败续办。

重试复用原删除流程及已有资源绑定，不重复操作已清理对象，不能因默认隐藏已删除任务导致用户无法查询或重试。管理页清理记录不等于恢复到可执行列表。

因在途执行未结束而正常延后资源清理，不等同于实际清理失败；延后清理的安全完成机制在执行生命周期中细化。

## 已解决 C4.1：再次分发遇到曾删除的子任务

某用户之前收到该源任务的子任务，之后该子任务被逻辑删除。新一轮分发名单再次包含该用户，应如何处理？本问题指明确的新分发，不是旧分发请求重试或迟到工作复活任务。

用户选择 1：明确的新一轮分发创建新的子任务 ID，旧记录保持已删除；新任务的资源及绑定与旧删除清理隔离，不恢复旧记录。新分发沿用自身已保存的目标身份，重试不能重复创建。

旧分发请求重试或迟到工作不属于新分发，不能因原子任务已删除而复活原任务或另建替代任务。

## 已解决 C4.2：异步分发部分失败后人工续办

本节保留澄清过程；人工续办方式已由 C4.4 的最新决定简化为通过新一轮分发重试，不再开发独立旧轮续办接口。下面的原轮快照复用规则仍适用于中断恢复，不适用于新一轮业务重试。

例如向 100 人分发，90 人成功、10 人失败，应如何继续处理实际失败的业务步骤？

用户选择 1：人工续办，保留成功结果，只重试失败或未完成步骤，复用原分发快照、目标身份和散列偏移；必要的批入口时间联动失败同样可以续办。不新增后台自动业务失败重试。人工续办仍由异步分发后台执行，不要求前端等待所有目标处理完毕。

平台结果不明先核对，不盲目重复注册。实例退出后的数据库领取、租约和进度恢复仍然需要，与本问题的业务失败自动重试不同。续办不能绕过当前删除、权限、配置版本和模式协调约束，原快照不构成覆盖新状态的授权。

## 已解决 C4.3：同一源任务分发串行

同一源任务已有一轮分发排队或处理中，是否允许再受理另一轮新的分发？同一次请求幂等重提不属于另一轮。

用户选择 1：不允许同时进行，返回正在处理的分发 ID 及进度；当前轮结束后才能发起下一轮。同次请求重复提交仍复用原分发，不误判为另一轮。后续 C4.4 将业务失败重试统一为新一轮，不再设置独立旧轮续办。

约束按包含 tenant/source/Agent 的完整源任务身份执行，由数据库协调多实例并发受理和领取，不能只禁用前端按钮或使用进程内锁。实例退出后仍待恢复的非终态分发不因本地工作停止就释放该约束。

## 已解决 C4.4：通过新一轮分发重试失败接收方

第一轮部分失败，之后已经受理新一轮分发，且新一轮可能使用不同散列参数。此时是否允许人工续办第一轮？

用户决定：“新一轮分发里重试就行了”。业务失败由人工选择接收方、使用新 request_id 发起新一轮分发，不另设旧轮续办接口。旧轮仍保存原进度及错误供查询；原 request_id 重提只返回原轮事实，不重新推进失败项。

新轮使用当前允许分发的源定义及本轮散列参数，不保证旧轮偏移不变。对未删除的已有子任务复用身份和有效资源、核对未完成步骤及结果不明的平台操作；不能因上一轮失败重复分配任务或资源。已逻辑删除子任务仍按 C4.1 新建隔离身份。旧轮迟到工作不能覆盖新轮。

不能丢弃旧轮已创建资源和未完成步骤的记录，不能把历史失败伪装为成功；停止旧操作推进不等于删除已经生效的子任务。批入口时间联动失败也需能通过新轮重算当前有效子任务及核对平台状态来收敛，不能只重做目标创建。

## 已解决 C4.5～C4.10：分发集中确认

用户答复：第 1、3、4、5、6 项按建议，第 2 项采用旧回退。对应规则如下，均已确认：

| 编号 | 问题 | 已确认规则 |
| --- | --- | --- |
| C4.5 | 散列算法和窗口 | 沿用现有按本轮目标顺序均匀分布、向源排程提前的算法，窗口保持 0～24 小时，不暗改为租户哈希 |
| C4.6 | Cron 无法安全平移 | 保留旧回退：使用原 Cron 和时区，实际偏移记为 0，并在目标结果明确告警；不因此单独判分发失败，也不虚报已成功应用散列 |
| C4.7 | 0 人调整散列的作用范围 | 对全部未删除关联子任务重算排程，包括停用子任务；只改排程/散列及必要平台联动，不改正文、不恢复启用、不创建任务 |
| C4.8 | 子任务被接收人修改后再次分发 | 沿用源定义覆盖内容和排程，但保留子任务身份、Chat/会话、启停和运行结果；与同时发生的独立更新以版本冲突保护 |
| C4.9 | 目标环境模型或 Workflow 不可用 | 模型沿用旧逻辑回退目标默认模型并告警；缺少必要 Workflow/技能配置则该目标失败，不宣称已可执行，不影响其他目标 |
| C4.10 | 分发中请求删除源任务 | 拒绝本次源任务删除并返回分发进度，等待分发结束后重试；拒绝时不写删除标记、不清理资源。不改变其他已确认的单任务删除及不自动级联规则 |

0 人模式在受理时固定待调整的未删除关联子任务集合和必要版本，包含停用对象；不是先重新复制源内容再覆盖回去。没有对象时不创建任务。普通含目标分发仍只处理所选接收方，不扩散到全部历史子任务。目标默认模型也不可用时不能虚报准备成功；模型回退不豁免必要 Workflow/技能配置校验。

分发与源删除需在数据库中协调并发受理：不能出现删除已通过、分发又被受理而继续创建子任务的竞争。再次分发的内容覆盖不覆盖并发运行结果；独立编辑的竞争用版本校验报告冲突，不以旧快照强写。

## 已解决 C5.1：外部失败提示并重试，不增加触发阻断

从普通调度切换到批调度等三态转换需要操作多个平台入口。部分入口同步失败时，是否保留待完成切换，还是回滚？

用户先选择保留进度人工重试，随后明确修正：“外部处理失败就提示并支持重试，但不阻止触发”。以该最新要求为准，撤销此前建议中的“切换未完成期间阻止该组新触发”。

保留目标状态、逐项成功/失败及错误，支持人工重试未完成步骤，不自动回滚、不新增自动业务失败续办；成功项不重复操作。结果不明先核对，不能盲目重复注册。查询明确展示同步未完成，不虚报整组平台已同步。

不得把外部同步待处理/失败标记作为整组新触发的独立阻断条件。该要求不等于忽略实际停用、逻辑删除、暂停批调度、权限或执行去重等业务规则，也不改变已有队列和运行继续的约定。此前内容更新 C3 的准备及生效门禁不因本条三态澄清自动取消。

切换的业务生效语义已按 R1 确认为逐对象临时混合：成功对象按新方式，未同步对象暂按原方式继续，重试后统一；暂停批调度、单任务停用和删除仍按数据库业务状态校验。具体平台绑定版本归属和跨入口去重在接口契约中细化，不能让普通与批入口为同一任务同一执行期各创建一次运行。

### R6：以共库状态确认执行，不等待完成回执

用户明确：“scheduler 应该不用收到回执吧，swe 直接去表里写结果就行了吧”。最终状态及结果只由 SWE 直接保存到共库，Scheduler 读表处理自身队列和批次，不要求 SWE 再发一次完成回调，不通过 HTTP 搬运或重复保存同一结果。

Scheduler 先保存本次执行身份并请求 SWE；SWE 在实际运行前按该执行身份持久登记受理/开始事实，结束后保存状态和结果。HTTP 正常响应可快速表达受理或拒绝，不等待 Agent/Workflow 完成，也不作为本次执行成功的依据。SWE 仅写自己负责的接收和运行事实，不代写 Scheduler 的队列和批次业务字段。

HTTP 触发请求仍可能未送达或响应丢失，这属于可靠派发问题，不是增加完成回执的理由。Scheduler 以同一执行身份查共库并幂等恢复，不因缺少 HTTP 响应就分配新执行身份重跑；同一请求并发或重复到达 SWE 不能重复启动。单次查无记录不能直接证明未送达，需要与幂等受理及安全接管协调。

实例退出、长期未完成和结果落库失败的判定与恢复在技术契约中说明，不承诺仅靠一张任务级状态记录即可判断所有执行，也不把额外人工核对页面或人工决定重跑当作用户已批准的业务功能。

### 无需重复决策的兼容规则和实现细节

- 批优先级复用现有用户优先、支行其次的排序及新批次快照规则；不增加接收方，不重排已入队批次。具体空值、重复项及不匹配对象按兼容契约处理，不新增优先算法。
- Workflow 配置版本随执行快照固定，已入队任务不切换到之后更新的配置；无需另问是否让旧队列改用新版本。
- 原通知、未读累计、配置化未读自动暂停的业务语义继续适配；状态写库，并按既定 SWE 运行事实与 Scheduler 管理控制的职责分工处理，不回填文件或旧展示内存。
- 标记已读清理本次已读边界内的已有未读，之后新结果仍未读；恢复也使用已确认的边界规则。删除、停用等独立规则不被标记已读解除。
- 删除等待在途执行结束属于正常生命周期，结束后安全完成资源清理；真正清理失败仍按已确认的人工重试，不把正常延后清理变成自动业务失败重试。
- 批量删除/立即执行组合单任务能力，逐项鉴权、返回逐项结果，某项失败不回滚其他项；不扩大智拓删除范围或引入新的批量执行语义。
- 分页、错误码、幂等键、字段级事务、索引及租约等作为接口契约和实现细节整理。DDL 继续只出手工执行方案，不直接操作业务数据库。
