# Scheduler 新版普通调度和批调度入口

日期：2026-10-14

开发基线：`v1.0.0`

状态：新版入口及新旧通道隔离方案已梳理，尚未实现

关联设计：

- [更新任务](2026-10-14-zhituo-scheduler-cron-update-flow.md)
- [删除任务](2026-10-14-zhituo-scheduler-cron-delete-flow.md)
- [分发及三态调度](2026-10-14-zhituo-scheduler-cron-broadcast-dispatch-state-flow.md)
- [任务及子任务查询](2026-10-14-zhituo-scheduler-cron-query-flow.md)

Scheduler 新增普通和批调度触发入口，不替换原批入口。新版普通能力先开发和验证，暂不接入真实调度；新创建的智拓批任务注册到新版批入口，存量批任务继续使用原入口、原派发协议和 SWE 的文件执行通道。

外部平台只负责按时间触发。Scheduler 接收触发、登记执行、入队和派发，SWE 实际执行 Agent、文本或 Workflow。不能将“平台已调用入口”或“SWE 已接收”表述为任务已经执行成功。

## 当前部署和切换边界

| 任务或能力 | 本阶段运行路径 |
| --- | --- |
| 存量普通任务 | 保持平台原入口，由 SWE 读取 `jobs.json` 执行 |
| Scheduler 新版普通调度 | 开发及受控验证，暂不绑定真实平台回调，不接管存量普通任务 |
| 存量批任务 | 平台原批入口 → Scheduler 旧表及旧派发协议 → SWE 原入口 → `jobs.json` |
| 新智拓批任务 | 平台新版批入口 → Scheduler 新表、快照和新派发协议 → SWE 新执行入口 |
| 新智拓任务后来切回普通调度 | 本阶段仍按原普通文件执行通道安排，不因此启用 Scheduler 新版普通入口 |

只有新批定时器注册时配置新回调地址，不批量修改存量平台任务地址，也不为普通任务增加 SWE → Scheduler 的转发。

智拓初次创建的任务使用批调度，不取消已经确定的 `ordinary` 三态选项。普通执行可保留文件依赖；新版批执行不能依赖异步兼容文件是否及时写入。

## 接口清单

以下是建议路径，精确字段、响应码和部署启用机制在实现前确定：

| 方法和路径 | 定位 | 本阶段启用情况 |
| --- | --- | --- |
| `POST /api/scheduler/cron/ordinary/callback` | 新版普通任务触发入口 | 先实现、暂不接入真实调度 |
| `POST /api/scheduler/cron/batch/callback` | 新版批父任务触发入口 | 新创建的智拓批任务使用 |
| `POST /api/scheduler/cron/callback` | 现有存量批父任务入口 | 保留原路径及协议 |
| SWE 新执行入口 | 接收 Scheduler 的执行定义快照和执行身份 | 配套新批通道；路径及契约另行细化 |
| `POST /api/internal/cron/callback` | SWE 现有文件执行入口 | 存量通道及本阶段普通执行保留 |

新版普通和批调度入口不是智拓直接发起的分发接口，也不是手动执行接口。分发生成任务定义，平台触发才生成本次执行工作。

## 身份及触发协议

新增接口的 tenant、source、scope、Agent、用户等身份上下文采用 header，沿用现有 SWE 相关接口的解析方式；不另起一套应用身份传递方式。平台回调具体封装和 header 生成需按平台及现有适配器核对。

新版回调正文只携带任务和触发相关标识，不接收外部传入的完整权威执行定义：

- 普通任务 ID 或批父任务 ID。
- 已注册的平台定时器标识。
- 本次平台触发的稳定标识或执行日志标识。
- 计划触发时间及必要平台回调字段。

Scheduler 根据任务完整身份读取数据库，校验平台绑定与任务归属。不能让回调直接指定别人的执行用户、Provider 密钥、Chat 或执行内容。

相同触发的重试必须能得到同一个执行或批次，不能每次用新 UUID 或到达时间代表新的执行。平台实际能够提供哪些稳定字段、缺失时如何建立确定性标识，在实现前核对。

旧入口继续接收原来的字段和封装，不能把新增 header 或快照字段无条件强加给存量调用。

## 新版普通调度入口

### 目标入参及响应

正文示例：

```json
{
  "job_id": "ordinary-job-001",
  "external_job_id": "91001",
  "trigger_id": "platform-trigger-001",
  "scheduled_fire_at": "2026-10-14T09:00:00+08:00"
}
```

以上是字段职责示例，不代表平台已经支持这些字段。身份信息放 header，具体回调适配不依赖示例 ID 格式。

受理响应需区分已接收、重复触发、未启用或任务不允许执行。例如：

```json
{
  "job_id": "ordinary-job-001",
  "execution_key": "execution-001",
  "definition_version": 3,
  "accepted": true,
  "reused": false,
  "status": "accepted"
}
```

`accepted` 只表示本次执行已登记或接收，不表示成功完成。未启用时应明确拒绝真实执行，不悄悄绕过开关或回退到旧文件路径。

### 内部流程

1. 检查新版普通能力的启用边界及调用上下文。本阶段不配置真实平台定时器指向它；受控验证方式在部署设计时确定。
2. 从 `swe_cron_jobs_v2`、`swe_cron_job_states` 读取完整任务身份、定义、准备结果和平台绑定。
3. 校验任务未删除、已完成必要准备、自身启用且允许普通新触发，检查定时器身份；重复触发查询既有记录，不重复执行。
4. 持久化本次执行身份、定义版本、定义快照和接收进度，再发起 SWE 执行请求，不以进程内状态代替执行幂等登记。
5. 通过复用的新执行编排能力调用 SWE，传入已有 Chat、会话及执行上下文，保持定时执行语义，不当作手动执行。
6. 保存接收及结果处理进度。超时不能直接认定 SWE 未执行，不在结果不明时盲目再次运行。
7. SWE 直接保存实际运行状态和结果关联；Scheduler 读取共库结果，收敛自己负责的执行登记进度，不代写一份相同的任务运行结果。

未来新版普通接入时可以复用新快照执行通道。具体是否建立独立普通执行意图、复用何种持久执行记录，以及配套字段和索引在实现前细化。

### 暂不启用的约束

- 不修改存量普通任务的平台回调地址和参数协议。
- 新版普通接口的存在不等于已完成普通路径切换。
- 不添加 SWE 普通回调转发 Scheduler 的分支。
- 本阶段新任务切回普通调度时，注册或恢复的普通定时器仍使用原 SWE 普通入口。
- 普通文件执行仍有异步文件写入延迟或缺失风险，不能按新版快照通道宣称已消除该依赖。

具体开关、测试启用及后续切换条件另行细化，不把现在的文档保存或将来的代码部署自动解释为普通新入口启用。

## 新版批调度入口

### 目标入参及响应

正文示例：

```json
{
  "parent_job_id": "batch-parent-001",
  "external_job_id": "92001",
  "trigger_id": "platform-batch-trigger-001",
  "scheduled_fire_at": "2026-10-14T09:00:00+08:00"
}
```

Scheduler 注册新智拓批父定时器时，将 URL 指向新版批入口，记录平台与父任务的绑定。存量定时器继续使用原 URL。

受理结果示例：

```json
{
  "batch_id": "execution-batch-001",
  "parent_job_id": "batch-parent-001",
  "accepted": true,
  "reused": false,
  "enqueued_intents": 100,
  "status": "queued"
}
```

这里的 `batch_id` 是定时任务执行批次，不是广播分发 `task_id`。队列条目数量不是已经执行完成的数量，也不套用分发 targets 的 0～1000 输入人数限制作为执行结果含义。

### 新批次接入流程

1. 解析并校验 header 身份、父任务及平台定时器绑定。
2. 从新定义和状态表查询父任务、三态配置及全部有效关联子任务，使用明确的关系和索引，不从旧表的 metadata 模糊匹配新任务。
3. 对未受理的新触发，只在 `batch_enabled` 下创建批次；`batch_paused`、`ordinary` 不创建新的批执行工作。重复已受理触发按已存记录幂等应答，不因此取消既有批次。
4. 根据任务准备、启用、删除状态等选出允许入队的执行对象；父任务自身是否参与执行沿用对应任务规则，批入口启停不混同于单任务 `enabled`。
5. 固定计划执行身份、任务定义版本和完整执行快照，保存批次及意图。Workflow 的必要配置版本也按已有批执行规则固定，不在派发时偷偷换配置版本。
6. 为批次及意图记录新执行协议标记，供后续派发和恢复正确选择通道。
7. 返回受理和入队结果，后续由 Scheduler 的队列派发能力调用 SWE，不等待整个批次完成。

散列仍由分发接口生成并持久化。批入口读取现有排程及实际偏移，处理逻辑计划时间与平台提前触发时间的对应，不重新计算子任务散列或扫全库判断到期。

### 已入队意图的派发流程

1. 根据批次和意图的新旧协议标记选择通道，保留现有容量、并发、领取和恢复能力的适用部分。
2. 对新意图校验领取身份、尝试次数和执行幂等信息，读取其入队快照，不再通过文件或当前新定义覆盖旧执行参数。
3. 不因当前变成 `batch_paused` 或 `ordinary` 拒绝已经入队的意图；不能沿用一个暂停字段同时停止新批接入和队列消费。
4. 调用 SWE 新执行入口，传入快照和必要执行身份。任务实际在 SWE 上执行，不在 Scheduler 运行 Agent。
5. 持久化接收及完成进度；响应丢失、连接超时、执行结果不明时先核对状态，不能盲目新增一次执行。

三态切换时，已入队继续派发，已执行继续完成；结果回写不恢复旧三态。未开始的任务遇到单任务逻辑删除不再派发，已经开始的允许完成。删除和权限校验是独立规则，不与单纯模式切换混淆。

## SWE 新执行通道的配套边界

SWE 新执行入口由 Scheduler 调用，不由外部平台直接用它派发每个子任务。具体路径及完整契约另行细化，必要内容包括：

- 唯一执行身份、定义版本和完整执行定义快照。
- 批次、意图、执行尝试等适用身份及防重复信息。
- 已准备的 Chat、会话和路由，必要的 Workflow 配置版本。
- 按原身份体系传递的 header 及必要追踪信息。

SWE 校验归属、执行登记和幂等身份后，复用现有执行器、超时、并发控制和追踪能力。不能先收快照再调用只按 ID 从 `jobs.json` 读取定义的原 `run_job()`，也不能在新执行中重新创建任务、注册平台或调用旧任务同步。

新批执行不依赖 `jobs.json`。旧 SWE `/api/internal/cron/callback` 和相应文件执行逻辑保留，用于存量及本阶段普通运行路径。

SWE 新通道还需保留原执行应有的会话、结果摘要、未读、通知和追踪行为，不能只调用底层 Agent 后丢掉这些业务效果。它们的状态写入和通知读取应与数据库新路径适配，不把兼容文件的完成当作权威结果。

## 执行结果和共库收敛

新路径由 SWE 按稳定执行身份幂等写入共用数据库中的执行结果，并直接更新 `swe_cron_job_states` 中对应的实际运行字段。一次执行保留一份结果记录，Scheduler 不接收后再重复保存相同结果，而是据此收敛自己负责的执行登记、意图和批次。

可以复用 `swe_cron_executions` 等现有结果表，但需要核对执行身份、版本、状态、快照关联及唯一约束。普通触发的持久幂等登记是否需要独立表，仍需在 SQL 设计中确定，不能把此前管理接口的三张新表当成完整运行闭环的最终表清单。

不因为三者共库而省略执行接收及结果登记，也不再通过 HTTP 重复插入一份相同执行记录。若接口通知用于加快状态收敛，应是通知或幂等更新，不是额外创建第二份历史。

状态收敛不能清除任务删除标记、覆盖新定义、重开旧模式或用旧快照重置未读状态。写入方按下节分工确定，具体字段、状态计算、事务边界及失败恢复在实现前细化。

普通文件执行在本阶段仍保持原入口。新任务切普通后，由 SWE 识别新任务归属并将该次执行的开始、完成和必要结果直接写入共库状态表，再兼容刷新内存；存量普通任务不切换写入规则。具体衔接字段仍需细化，不能假设尚未启用的新版普通入口已经接管了该反馈。

新任务状态先持久化，再通过独立适配层尽力投影到 SWE `_states`，兼容旧查询；兼容请求携带目标用户 Header 经过网关，只更新命中的实例，旧查询不增加逐次查库回填。普通旧通道要补齐正确的普通平台绑定并衔接执行结果、自动暂停的权威写入，不能仅写内存。投影不影响并发信号量等运行对象，未来可单独删除，详见 [内存兼容方案](2026-10-15-zhituo-swe-cron-memory-compatibility.md)。

## 执行状态写入分工与并发约束

`swe_cron_job_states` 不限定整张表只能由一个服务写，而是按业务动作和字段划分责任。以下为字段语义分组，不代表已经确定物理列名。

| 动作或数据 | 写入方 | 写入边界 |
| --- | --- | --- |
| 创建初始化 | Scheduler | 首次建立状态记录并初始化必要运行字段；创建重试不得重置已产生的运行结果 |
| 更新、准备绑定、平台同步、暂停恢复、三态切换、删除清理 | Scheduler | 只修改本次管理操作负责的字段，保留实际运行结果 |
| 执行开始、成功、失败、实际取消或跳过、运行时间、错误及必要结果关联 | SWE | 直接写运行字段及执行结果；不修改定义、平台绑定、三态、删除或管理进度 |
| 执行产生的摘要、未读等展示状态 | SWE | 按执行身份幂等更新，不因完成事件重试重复增加未读；与标记已读等操作协调 |
| 自动暂停 | SWE 与 Scheduler 分段处理 | SWE 记录实际执行触发的原因和待处理事实；Scheduler 负责调度控制字段及平台变更，分别表达请求和处理进度 |
| 执行登记、队列意图、批次及分发后台进度 | Scheduler | 属于各自工作流，不等同于任务运行状态，不要求 SWE 修改这些调度记录 |

SWE 的创建、更新准备接口和删除资源清理接口仍不代写 Scheduler 的管理字段；只有实际执行路径按职责写运行状态。完整对话、报告等执行产物沿用原存储，状态表只保留查询所需的状态、摘要或关联，不复制整份产物。

执行先持久化状态、再更新内存兼容副本。SWE 已在处理请求的实例上执行时，提交后直接调用本机兼容适配层，无需为更新相同状态再请求 Scheduler，或让 Scheduler 调回 SWE。Scheduler 管理操作提交后，仍经网关携带目标用户 Header 通知 SWE 刷新兼容投影。

共享数据库的更新必须遵守：

- 使用完整任务身份和字段级更新，禁止读出旧状态后整行覆盖；更新默认值不得覆盖另一方拥有的字段。
- 每次执行使用稳定执行身份（以下记为 `execution_id`），重复开始、完成或结果写入保持幂等；任务定义版本不能替代执行身份。
- 各次执行结果可分别保留，但任务级“最近运行”投影需校验当前执行身份及明确的执行顺序。较早执行的迟到结果不覆盖较新状态；同一次执行也不能从终态回退到运行中。
- 多个执行并行时，运行中展示及最近结果的归约规则需明确，不能简单用最后到达的请求覆盖；重试、恢复还需识别过期执行尝试。
- Scheduler 的逻辑删除优先。已开始的 SWE 执行可完成并保存自身结果，但不能清除删除标记、重新插入已清理的任务状态记录或恢复文件、内存投影；已删除且未开始的任务不启动。
- 状态持久化失败不同于兼容投影失败：前者需要保留可恢复的执行结果并按执行身份重试，不能仅写内存就宣告状态已落库；后者只记录兼容错误，不回滚已提交业务状态。

Scheduler 通过共库结果处理队列、批次收敛；若保留完成通知，只用于加速处理，不重复插入结果或代写 SWE 运行字段。通知缺失或重启后的收敛恢复方式需单独细化，不能依赖一次不可靠通知保证最终完成。

该分工只用于本次新任务路径，不统一改造存量写入规则。

## 新旧任务及队列隔离

| 维度 | 存量通道 | 新智拓批通道 |
| --- | --- | --- |
| 平台批回调 | 原 Scheduler callback | 新版 batch callback |
| 任务定义 | 原 `swe_cron_jobs` 等既有来源 | `swe_cron_jobs_v2`、`swe_cron_job_states` |
| 队列协议 | 原标识和字段 | 新协议标记、执行身份及快照 |
| SWE 接收 | 原 callback、按文件执行 | 新入口、按入队定义执行 |
| 暂停和模式规则 | 保持原通道规则 | 三态只管新触发，已有队列继续 |
| 兼容文件 | 原任务数据来源 | 新批通道只作兼容副本 |

隔离不能只靠入口 URL：领取、派发、恢复和结果收敛均需识别新旧协议。旧记录没有新版标记时按明确的旧协议处理，不能交给新处理器后因缺少快照失败。

新任务不因新表查不到就回退成旧任务；存量任务也不能统一要求在新表中存在。新协议标记的字段和默认值在实现时确定，不能把修改一个公共函数视为已经自动隔离两条路径。

## 启用和平台注册安排

- 本阶段仅为新创建的智拓批父定时器指定新版批 URL。
- 存量批任务不改平台记录，不强制补齐新回调协议或迁移数据。
- 新版普通入口先实现和验证，真实普通定时器不指向它。
- 切回普通调度时使用原普通平台入口，复用已有普通定时器或按需注册，不增加 SWE 转发。
- 旧 SWE 管理路径不能重复补注册 Scheduler 管理的新任务，但标记也不能拦住本阶段允许的普通文件执行。
- 异步兼容文件仍不等待、不回读；普通文件执行的延迟风险与新批无文件依赖分别说明。

## 验证场景

- 存量批回调仍能读取旧任务、入旧队列并调用原 SWE 文件入口。
- 新批回调只读取新任务，平台重复请求不产生第二个批次或重复执行。
- 新批执行在兼容文件缺失或过期时，仍按合法入队快照执行。
- 开启批调度后暂停入口，不接收新批次，但已入队和执行中的任务继续。
- 从批切普通后，旧的新协议批队列继续走新快照通道，后续普通触发走本阶段旧普通通道。
- 已入队任务在定义更新后仍用原快照；任务逻辑删除后未开始的停止派发，已开始的正常结束。
- 响应丢失、超时和实例重启不盲目重复运行，也不把结果不明误记为成功。
- 新旧结果在共库中各自正确收敛，不重复创建历史，不将删除状态或新配置覆盖回旧值。
- Scheduler 更新配置或三态与 SWE 执行收尾并发时，各自只更新负责字段；较早执行的迟到结果、重复完成及过期尝试不覆盖新状态或重复累加未读。
- SWE 直接写运行状态，Scheduler 读取结果后只收敛自身队列和批次；兼容投影失败与业务落库失败分别处理，删除中的在途结果不恢复任务。
- 新版普通默认未接入，部署新代码不会自动修改现有普通定时器 URL 或新增转发。

## 实现前需要细化的内容

- 新版普通、批入口及 SWE 新执行入口的最终路径、header、正文和响应契约。
- 平台稳定触发标识和计划时间的实际支持，新回调模板及注册绑定校验。
- 普通能力的禁用、验证及后续启用机制，不改变本阶段真实入口安排。
- 执行幂等登记和快照的表、字段、唯一约束，以及队列新旧协议标记。
- 普通、批及模式转换时的同次执行去重，散列提前触发与逻辑执行期的对应。
- 批队列恢复、接收确认、结果不明处理，以及删除与即将开始执行之间的并发边界。
- 执行结果写库和状态收敛事务，通知、未读及普通旧通道的最小状态衔接。
- 新旧队列的容量、领取和派发分流方式，不借此全量改变存量规则。
