# 批调度看板（新）完整复刻设计

## 一、已确认的目标与边界

用户要求新增独立的“批调度看板（新）”，复刻现有批调度监控页面，并选择完整保留失败分类和人工批量重试，而不是只做只读页面。

用户于2026-10-17明确要求开始开发，本设计已确认实施。当前进度另见实施计划与进度记录；接口和页面不能因设计被接受就视为已完成。它是本次旁支需求，不表示父线程全部迁移工作已经完成。

1. 旧页面、旧接口和旧队列协议不变，新旧入口分别保留。
2. 新页面延续老页面的 Ant Design、CSS Modules、布局、间距、表格、筛选、加载和提示方式，不另起视觉设计。
3. 新页面只展示新链路批次和执行记录；模型池策略与容量是共用资源，明确标注共享口径。
4. 查询由 Monitor 完成，人工重试由 Scheduler 受理，SWE 仍直接写共库执行事实，不增加最终结果回调。
5. 人工批量重试使用专用新接口，不调用旧失败重试接口，不把新任务塞进旧队列。2026-10-22 用户追加新版批成员自动重试：首次加两次自动重试、明确失败后等待五分钟，超时沿用旧版回收规则，鉴权过期、用户不匹配与技能任务结果不可用不自动重试；详见部署文档。

实现时只修改该功能必需的局部文件；不启动子代理，不改 Git 分支、不暂存、不提交、不推送，不覆盖主线程其他改动。业务表结构仅提供手工 SQL，不自动执行 DDL。

## 二、方案选择

推荐采用“独立新页面、新查询契约、新人工重试接口”的方案：前端复用老样式与适用的纯展示组件，查询和操作全部有明确的新链路归属，执行事实仍来自共库。

其他方案不采用：

- 只在前端把新执行记录拼进老接口：无法正确完成全局筛选、分页、最新尝试归约和整批统计，且容易误调用旧写接口。
- 给新任务同步写旧批次及旧队列表：可能被旧处理器领取，破坏新旧隔离，不作为看板兼容手段。

## 三、页面复刻范围

新入口建议为 `/monitor/cron-batch-dispatch-new`，菜单与页面标题使用“批调度看板（新）”。旧 `/monitor/cron-batch-dispatch` 保留。

### 1. 批次概览与列表

- 保留今天、近 24 小时、近 7 天、自定义时间范围和状态筛选。
- 保留批次数、逻辑执行成员数、运行中批次、完成率、失败成员和有效 worker 等概览布局。
- 保留全局关键词筛选、计划时间倒序、服务端分页及当前批次选择联动，不将本页筛选冒充全局筛选。
- 新批次由已受理的批触发回执识别；普通执行、普通手动执行和“分发给接收人”的分发任务不混入实际执行批次。
- 没有生成批次的已跳过平台触发，不伪造为一个执行失败的 Batch。

### 2. 批次详情与执行成员

- 保留父任务、批次身份、计划及收到回调时间、执行进度和状态。
- 保留父/子角色、状态、关键词筛选，明细和事件各自独立分页；详情筛选不改变整批统计。
- 保留批内顺位、用户/分行优先信息、模型池、时间和公开错误信息；未实际记录的热度或 owner 显示缺失，不能伪造为有效数值。
- 批内顺位表示受理时冻结的计划顺位，不冒充跨实例、跨任务的实际开始先后；实际开始以执行事实时间展示。
- 执行记录使用真实字符串 execution_id，不将 UUID 转成旧数字 Intent ID；界面可继续使用原列布局和缩略展示。
- 每个逻辑成员默认显示最新业务尝试；原失败与重试过程可从事件及执行历史追溯，不增加总成员数。

### 3. Worker、策略与容量

- 保留 source 维度模型策略、当前容量、容量曲线和调整记录。
- 容量历史完整遍历服务端游标；中途失败明确提示不完整，不能画成完整曲线。
- 策略和容量配置继续读取现有共用模型池表，不复制一套配置。
- 新批次统计只计新执行；共享模型池的占位同时考虑新旧队列，界面明确说明“共享模型池”，不把共享容量说成新任务专属容量。

### 4. 失败分类与人工批量重试

- 保留整个批次的失败分类计数、分类多选、前 200 个匹配成员预览、刷新与提交中防重复点击。
- 保留执行结果未知、超时等危险类别的“已核对原执行及其子任务已停止”确认，不将人工确认当作系统已证明外部工作未发生。
- 保留逐项受理与状态已变化跳过的反馈；重试后刷新列表、详情和失败预览。
- 新接口只接受失败成员，不把已取消、已跳过、正在运行、已经成功或已经被后续尝试替代的记录当成失败重跑。
- 所有失败类型来自公开错误码或明确的执行侧分类；当前未保留的原因只能显示为“其他错误”，不能根据不存在的原始错误编造分类。

## 四、数据来源与统计口径

| 数据 | 新看板来源 | 说明 |
| --- | --- | --- |
| 实际批次及固定成员 | swe_cron_managed_trigger_receipts | kind=batch 且具有真实 batch_id；原成员清单不因重试改变 |
| 可索引的成员关系及当前尝试 | 拟新增 swe_cron_managed_batch_members | 由真实受理成员登记，关联当前执行，不复制执行状态 |
| 排队、派发、受理、运行和结果 | swe_cron_execution_runs | 按逻辑成员归约最新业务尝试 |
| 父子任务、定义及当前控制状态 | swe_cron_jobs_v2、swe_cron_job_states、swe_cron_managed_dispatch_controls | 完整 tenant/source/Agent/job 身份关联，不凭裸 ID 授权 |
| 已有最终执行历史 | swe_cron_executions | 继续通过 history_execution_id 关联，不修改旧历史结构 |
| 策略与容量 | 现有模型策略、scope 租约和 worker capacity 表 | 共用资源，非新批次专属 |
| 新链路事件与人工重试审计 | 拟新增 swe_cron_managed_dispatch_events | 与旧 swe_cron_dispatch_events 隔离 |

列表、详情、失败预览采用同一个逻辑成员与最新尝试口径，不能各自选出不同的“当前状态”。概览和分页总数在数据库中按完整查询范围计算，不根据当前页加总。

普通/批入口同逻辑期会复用同一个执行 ID，因此批成员可能引用一条最初由 ordinary 入口创建的运行。只按 runs.kind=batch 或运行元数据中的 batch_id 筛选会漏数；批次归属必须以触发回执的真实成员关系为准，未被批次引用的普通执行仍不混入看板。

原始状态按事实显示：queued、dispatching、accepted、running、success、error、dispatch_failed、skipped、cancelled。标签、筛选和值必须对应，不能把 accepted 显示成已经成功，也不能把 dispatch_failed 当作已经发生的业务失败。

批次归约规则：有执行中/受理中/派发中成员则为进行中；否则仍有 queued 或派发未确认成员则为等待处理；全部成员已有明确终态后，存在业务失败则批次失败，否则完成。零成员批次保留“已接收、无可执行成员”的含义，不伪造成功率。

“外部批入口暂停”与“队列暂停”严格区分。新模式暂停只关闭未来平台入口，不取消已经受理工作，也不应沿用旧页面“后续调度已暂停”来暗示已有队列停止。

时间查询与输出统一：新执行事实为 UTC，旧共用容量记录沿用既有北京时间；服务端按业务时区解释不带时区的筛选值，响应给出明确时区。前端不直接混排两类裸时间。

## 五、人工重试的目标契约

### 1. 接口分工

以下均为拟新增接口，路径在实现前核对现有路由，不覆盖旧路径。

| 服务 | 方法和路径 | 职责 |
| --- | --- | --- |
| Monitor | GET /api/monitor/cron/managed-dispatch/batches | 新批次全局筛选、分页及概览 |
| Monitor | GET /api/monitor/cron/managed-dispatch/batches/{batch_id} | 当前成员和事件的独立筛选分页 |
| Monitor | GET /api/monitor/cron/managed-dispatch/workers | 共用策略、当前容量及游标历史 |
| Scheduler | GET /api/scheduler/cron/managed-dispatch/batches/{batch_id}/failures | 失败分类与本次可操作成员预览 |
| Scheduler | POST /api/scheduler/cron/managed-dispatch/batches/{batch_id}/retry | 显式人工重试、请求幂等及逐项结果 |

Monitor 新查询不写状态、不调用平台、不扫描工作区；Scheduler 重试只持久受理，新后台领取后再调用 SWE，不在监控请求里直接执行 Agent/Workflow。

### 2. 业务重试与运输恢复分开

| 当前事实 | 人工操作 | 执行身份 |
| --- | --- | --- |
| 派发未确认、尚未被 SWE 受理 | 提前再次投递同一次请求 | 保留原 execution_id、原快照，不新建业务尝试 |
| SWE 已明确记录业务执行失败 | 新受理一次批次成员的业务执行 | 新 execution_id，关联原成员和原批次，保留失败记录 |
| 已运行、已成功、已跳过/取消或已被后续尝试替代 | 跳过并说明 | 不创建新执行，不复活原运行 |

业务重试仍属于原批次成员，不另建整个人员批次；一次管理员点击最多为每个被选择的当前失败成员增加一次新尝试。2026-10-22 起自动工作域也可在未达三次总尝试且满足错误/状态条件时受理下一轮；人工操作仍可显式超过自动上限。看板只显示 business_attempt-1，不显示技术投递次数。

新的业务尝试在受理时使用当前有效任务定义和当前已发布 Workflow 配置，并再次冻结；预览展示原执行版本和当前版本，提交校验预览中的当前定义版本，避免悄悄执行刚被他人修改的正文。原始运行、仍在排队的运行和运输重投的快照不改变。

这种“人工重试批任务”不等同于脱离批次的普通手动执行按钮：保留该批次逻辑计划时间，新最早执行时间为本次人工受理时间，结果继续遵守批任务的未读/通知规则。记录本次真实管理员，不冒充接收人。

### 3. 受理、安全及幂等

- Header 沿用现有真实用户、source、角色及认证链路。前端隐藏入口不是授权；服务端校验真实 manager/admin 和 source 范围，Body 不授予跨 source 权限。
- 请求包含稳定 request_id、1～200 个明确候选及预览版本、必要的停止确认。目标身份由批次成员和共库数据确定，不能只凭 execution_id 或前端 tenant 声明任意重跑任务。
- 同请求原 Body 重提复用原结果；同请求换候选或确认内容返回 409。两位管理员并发处理同一失败成员时，只有仍为最新失败的成员可新增一次尝试，另一请求明确跳过。
- 候选去重；不存在、非本批次或其他 source 的对象不泄露信息。任务已删除、停用、自动暂停、管理更新未就绪或定义版本变化时不自动恢复、不强行执行。
- 批入口暂停只影响未来平台触发；人工重试是显式操作，单任务满足执行条件即可受理，提示其不依赖重新打开外部批入口。它不改变当前普通/批调度模式。
- 对前置格式/权限/批次归属问题拒绝整批；可安全判定的成员状态变化逐项返回。存储异常必须保留真实不确定性，不伪造全部成功或全部未受理。

重试请求、每项决定和实际受理身份在同一事务中持久化，利用新事件表的唯一请求事件键保存请求摘要及响应，不另造异步“重试批任务”。网络响应丢失后使用原 request_id 和原 Body 核对，不换 ID 盲目再提交。事务内不执行平台 HTTP 或业务执行器。

## 六、需要补充的数据结构与执行侧支持

### 1. 执行尝试关联

拟新增 swe_cron_managed_batch_members，将回执中真实成员关系正规化为可索引记录。至少保存 batch_id、稳定 member_id、完整 tenant/source/Agent/job 身份、current_execution_id、business_attempt、受理时计划顺位和并发版本。member_id 使用首轮关联执行身份，后续业务尝试仍属于该逻辑成员。

成员表只保存关系和当前尝试指针，不复制 queued/running/success 等执行状态；状态始终从 swe_cron_execution_runs 读取。初次受理批触发时在原事务中登记关系；人工业务重试在同一事务中增加新运行、推进成员指针并写审计，运输恢复不推进业务尝试数。

批次与逻辑成员有唯一约束；推进指针时校验预览中的最新执行身份及尝试号，避免重复重试。最新尝试通过成员关系 JOIN 执行主键查询，不按每个成员分别请求一次数据库，也不依赖无索引的全量 JSON 扫描。历史尝试身份保存在新运行的重试关联元数据及持久审计事件中。

已有新链路记录需要从真实触发回执的固定成员清单回填关系，不能只从运行的入口类型推断。发现缺失执行、身份不符或异常关系须明确报告，不猜测父子身份，不将缺失状态当作已完成。具体建表和回填 SQL 单独整理给人工执行；不要求为此修改 swe_cron_executions 结构。

### 2. 新链路事件与错误分类

新增独立事件表保存真实排队、派发、受理、开始、结果和人工重试事实。事件需要完整身份、批次/执行关联、事件类型、真实时间、稳定去重键及已脱敏的必要详情。

事件由对应事实的写入方在原事务内记录：Scheduler 写受理、派发和人工重试事件，SWE 写实际受理、开始和结果事件。不得要求 SWE 回传最终结果，也不能把 Monitor 查询动作当成业务事件生产者。

升级前未记录的逐次派发细节不能从当前状态还原成完整事件历史；可以展示明确保留的时间事实并注明来源，但不能伪造丢失事件。失败分类在异常仍位于执行侧内存时生成公开分类码，再持久化；不保存或回显原始凭据、完整任务正文及未脱敏异常。

执行侧事件记录点及重试受理与主线程当前开发文件有交集；实现前再次检查工作区，只做必要小范围接入，保留其他改动，不用整文件覆盖主线程的执行器、派发器或生命周期代码。

## 七、实现组织与验证

前端：新增独立页面目录、请求适配器与类型，复用旧 CSS 和适用的 worker 纯展示组件。路由、两种侧边栏模式、导航高亮和中文标题一起接入。旧页面不复用新写接口，新页面也没有旧接口失败兜底。

Monitor：独立新路由、模型和查询服务，避免往旧大查询服务里混入新旧状态机判断。复用现有共用策略/容量的只读能力；新批次查询只读新链路。

Scheduler/SWE：新增批次失败预览和人工重试服务，增补最小的执行关联、事件与公开错误分类记录。新执行继续交给既有新链路的容量、优先级、租约和结果恢复流程，不实现第二个执行队列或计时器。

必须验证：

1. 新旧页面请求隔离，真实 Header 授权和跨 source 拒绝；新表缺失返回明确不可用，不返回假空列表。
2. 全局筛选、独立分页、完整容量历史、source/批次切换后的迟到响应隔离、卸载后不继续更新。
3. 相同批次多次人工重试保留历史但不膨胀成员总数；同请求、并发管理员、过期预览、定义变化及网络响应丢失不会重复受理。
4. 业务失败只经显式点击产生新尝试；运输未确认仍复用原执行身份，已运行工作不取消，停用/删除对象不复活。
5. 数据库事务、唯一约束、实际执行事件与结果原子性；共享池占位不重复计数；未完成主线程能力不被看板代码绕过。
6. 原页面和新页面的 Vitest、TypeScript、构建及一轮浏览器对照截图；数据库及平台未实测的部分单独注明，不能以 Mock 页面等同真实联调。

新文件、关键代码注释及接口说明使用中文。关键调用日志记录批次、请求、执行身份和安全结果码，不输出认证 Header、派发租约值或完整业务内容。复杂度上限继续为 15。
