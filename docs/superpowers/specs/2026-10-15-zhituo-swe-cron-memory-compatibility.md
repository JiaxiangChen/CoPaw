# 智拓定时任务：SWE 内存状态兼容方案

状态：设计约定，尚未开发。范围仅为 Scheduler 管理的新智拓任务；存量任务保持原机制。

## 结论

与 `jobs.json` 一样，为新任务保留可独立移除的 SWE 内存兼容写入。数据库是新任务的权威来源，内存只是供旧接口使用的临时投影。

新状态先提交到共用数据库，再尽力更新 SWE 的 `_states`。兼容写入失败只记录错误，不回滚已成功的数据库操作，不等待跨实例全部同步，也不以回读内存作为业务成功条件。

这不会把新任务的状态主存储重新迁回 SWE，也不改变本阶段存量执行入口的安排。

## 模块边界

建议设置独立的 `LegacyCronStateWriter`，与 `LegacyJobsFileWriter` 并列，分别控制启用和移除。名称为设计建议，不代表已有实现。

| 部分 | 职责 |
| --- | --- |
| Scheduler 管理写入 | 初始化状态记录，维护定义、准备绑定、平台同步、调度控制及删除管理字段 |
| SWE 执行写入 | 实际执行时直接持久化运行状态、时间、错误及必要结果关联，不覆盖管理字段 |
| 内存兼容适配层 | 将已提交状态映射到 SWE 当前实例的 `_states`，或删除对应投影 |
| 文件兼容适配层 | 尽力维护 `jobs.json`，不承担新批调度的权威读取 |
| SWE 旧查询 | 沿用本机内存读取和原响应结构，不新增逐次查库回填 |

SWE、Scheduler、Monitor 共库。兼容请求只用于刷新内存，不承担状态回传或权威数据复制；收到请求的 SWE 实例可凭完整任务身份从共库取得最新已提交状态。

兼容层不得注册、暂停或删除平台定时器，不得调用旧 `create_or_replace_job()`，不得隐式触发 Monitor 同步。平台操作仍属于既定业务流程。

## 写入时机与顺序

管理操作的顺序为：Scheduler 提交数据库 → 经网关发出兼容刷新提示 → SWE 从已提交数据构建本机内存投影。实际执行的顺序为：SWE 直接提交运行状态和结果 → 调用本机兼容适配层。无需为了更新相同运行状态再回传给 Scheduler，或由 Scheduler 调回 SWE。

执行状态的必要持久化不是尽力写，只有后面的兼容投影是尽力写。状态字段归属、执行身份、迟到结果及删除约束统一见 [执行状态写入分工](2026-10-14-zhituo-scheduler-cron-execution-entry-flow.md#执行状态写入分工与并发约束)。

| 场景 | 数据库提交之后的内存兼容动作 |
| --- | --- |
| 创建、准备完成、取得平台绑定 | 初始化可供旧查询使用的状态，补齐正确的平台绑定 |
| 更新定义、暂停恢复、三态切换 | 更新受影响的展示字段，保留已有运行结果，不重置为默认状态 |
| 执行开始、成功、失败、跳过、取消 | 按已持久化的执行状态刷新对应时间、状态及错误 |
| 自动暂停、未读及结果变化 | SWE 提交执行原因、未读或结果后刷新对应展示；Scheduler 完成暂停管理变更后再刷新相关控制状态，不混淆请求与完成；不把所有字段误当成 `_states` 字段 |
| 逻辑删除 | 清除或隐藏对应内存投影，并拒绝迟到刷新使其复活 |

分发中的每个接收方复用上述边界。分发进度和明细仍直接持久化，不新建内存分发账本。

同一任务的定义版本不足以排序多次运行状态：兼容刷新还需单调状态修订号或等价的提交顺序约束，并结合执行身份、删除标记处理迟到事件。确切字段和事务边界在实现前确定，不以消息到达先后覆盖状态。

## 哪些数据兼容到哪里

`CronJobState` 当前包含 `next_run_at`、`next_run_times`、`last_run_at`、`last_prefetch_at`、`last_status`、`last_error`、`external_job_id`。只投影有对应语义的数据，不虚构尚未产生的时间。

旧状态枚举只支持 `success/error/running/skipped/cancelled`；新状态映射必须显式处理，例如超时在旧响应中可表达为 `error` 并附错误信息，不能输出旧模型无法解析的值。最终映射在实现时与响应模型一起确认。

Chat/session、未读、结果预览、暂停原因等目前主要来自任务 `meta`，不是 `_states`。这些字段共用明确的兼容映射：文件副本尽力更新，旧响应可按数据库最新值覆盖对应展示字段。不能承诺只写 `_states` 就能兼容全部前端状态。

普通定时器 ID 与批入口 ID 必须区分。不得将批入口 ID 填入旧普通任务的 `external_job_id`，否则旧自动暂停逻辑可能操作错误的平台定时器。

## 网关路由与旧查询

按当前网关约定，相同用户信息 Header 的 SWE 请求固定命中同一实例。因此只更新收到兼容请求的实例，不做实例间广播，也不增加查询时跨实例回填。

1. Scheduler 调用 SWE 的准备、执行和兼容刷新接口时同样经过网关，携带与该任务用户一致的路由 Header，不绕过网关直连任意实例。
2. 分发给其他用户的子任务使用接收方的身份及路由 Header，不能统一使用源任务创建人的 Header；同时沿用现有权限校验，不把路由 Header 本身当作授权。
3. SWE 按完整的 scope / Agent / 任务身份更新本机投影，不能只凭裸任务 ID；旧前端列表、详情和状态接口沿用原有本机读取方式。
4. 新任务删除后清理本机投影，迟到刷新不得恢复已删除任务。兼容刷新失败时旧界面可能暂时陈旧，但数据库和新批执行不因此回滚。

实例重启或网关重新分配会丢失原内存，属于独立的恢复问题；粘性路由不等于内存持久化。不为此强制增加每次查询查库，可在实现前单独确定启动或首次加载时的数据库状态恢复方式。

兼容刷新只修改临时内存，不写业务表、文件或调度平台。新 Scheduler 查询接口仍保持数据库只读，不承担 SWE 缓存修复。

文件异步兼容不保证立即完成，因此旧的文件任务列表仍可能暂时缺少新任务；内存投影不能单独解决列表完整性。若要求新任务立即出现在旧列表，需在旧列表适配中合并数据库管理的新任务并去重，属于独立的读取兼容工作。

## 执行与旧写接口的边界

新批执行仍按入队快照运行，不依赖内存或文件投影成功。SWE 直接将实际运行状态及必要结果写入共库，提交后刷新本机兼容投影；Scheduler 读取共库结果维护自己的队列和批次，不重复保存相同运行结果。

新任务临时切普通调度时仍走旧 SWE 文件执行入口。这条路径也必须识别新任务，由 SWE 将执行开始、结束及必要结果直接写回共用状态表，再刷新兼容内存；不能只有内存变化而让新状态表长期停留在旧值。存量任务原写入机制不变。

旧自动暂停代码会从 `_states.external_job_id` 取得平台绑定，因此普通执行前需补齐正确绑定。新任务自动暂停由 SWE 保存执行原因和待处理事实，Scheduler 负责调度状态及平台变更；具体处理和恢复方式在实现前细化，不能直接照搬旧逻辑绕过 Scheduler。这是执行兼容衔接，不是让内存写入器调用平台。

前端旧的标记已读、暂停、恢复等写接口，若仍允许操作新任务，也要接到新任务权威写入逻辑，不能只改文件或内存。内存兼容层本身不解决这些写接口的归属。

## 可以删除什么，不能删除什么

后续新任务的查询与业务判断全部改读数据库，且普通旧通道也不再依赖兼容状态后，可以移除新任务的内存投影调用及其专用版本记录，再删除适配模块。

`CronManager._rt` 的并发信号量、锁和真实执行中的运行对象不是展示状态缓存，仍需保留。逻辑删除或清理投影不能撤销已开始执行，也不能提前销毁它们使用的运行资源。

存量任务原有 `_states` 写入要等其自身迁移完成才能删除；不能因智拓新路径切换完成就全局移除。

无需为此引入 Redis、新缓存表或分布式内存同步系统。文件、内存兼容分别收口，后续分别移除，不让删除兼容层牵动核心业务。

## 验证要求

- 创建、更新及平台绑定后，旧详情和状态接口返回正确的新任务状态，且不重复平台注册。
- 新任务执行前后，数据库状态正确；旧接口展示对应状态、运行时间、错误和结果。
- 相同用户 Header 的兼容请求与前端查询通过网关命中同一 SWE 实例，分发子任务使用接收人 Header，完整身份不同的任务互不污染。
- 模拟兼容写入失败，新批调度和数据库状态仍正确；后续兼容刷新可以更新投影，旧查询不承担逐次查库修复。
- 实例重启或路由重分配的恢复方式单独验证，不将固定路由视为状态已持久化。
- 迟到执行结果不覆盖较新的状态，迟到创建或刷新不恢复已删除任务。
- 新任务切普通后，正确补齐普通绑定，执行结果及自动暂停不只留在文件或内存。
- 关闭内存兼容时，数据库和新批执行不受影响；旧前端依赖未切走时，不宣称旧界面仍完全兼容。
- 存量任务的查询、执行及原有内存状态更新保持不变，并发控制和在途执行不受投影清理影响。
