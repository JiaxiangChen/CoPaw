日期：2026-10-14

开发基线：`v1.0.0`

状态：接口职责、异步分发、三态行为及散列归属已梳理，尚未实现

修订：2026-10-15，按[第二阶段最新边界](2026-10-15-zhituo-scheduler-cron-phase2-boundaries.md)取消文件、旧内存投影；Scheduler 新任务的普通与批调度均使用新版入口。

- [创建定时任务流程](2026-10-14-zhituo-scheduler-cron-create-flow.md)
- [删除定时任务流程](2026-10-14-zhituo-scheduler-cron-delete-flow.md)
- [更新定时任务流程](2026-10-14-zhituo-scheduler-cron-update-flow.md)

智拓调用 Scheduler 分发定时任务，并通过独立接口设置源任务及关联子任务的调度状态。分发异步处理，结果持久化；调度状态切换不取消已入队或正在执行的任务。散列参数只放在分发接口，三态切换不重新计算子任务散列排程。

以下接口路径、字段和响应示例表达目标契约，具体类型、默认值、错误码及表字段在实现前细化，不代表当前 `v1.0.0` 已支持。

## 已确认的边界

- 智拓是独立应用，通过 Scheduler HTTP 接口使用定时任务能力，不直接调用 SWE 内部函数。
- 没有存量智拓任务，不增加旧任务或 `jobs.json` 查找兜底。
- 分发是为接收方创建或更新独立子任务，不是立即执行 Agent 或 Workflow，不包含 Market 的技能和 MCP 分发。
- 分发与开启、暂停批调度及切换普通调度分开，不再由分发参数隐含切换整组调度模式。
- 分发采用异步处理；`/broadcast/tasks/current` 是必需接口，不是可选能力。
- 三态为 `batch_enabled`、`batch_paused`、`ordinary`。
- 已入队的定时任务继续派发，正在执行的任务继续完成，不清空队列、不取消、不重启。
- `enable_offset`、`offset_window_hours` 放在分发接口，不在三态接口重复传入。
- 数据库是权威数据源。新任务不补写 `jobs.json` 或 SWE 旧内存。
- 外部调度平台负责时间触发，Scheduler 不新增扫描全部任务定义以判断到期的调度器。

## 接口清单

统一前缀为 `/api/scheduler/cron/jobs/{job_id}`。`job_id` 是源任务 ID，所有接口还需要明确源任务的 scope、Agent，并按可信调用身份校验权限。

| 方法和路径 | 职责 |
| --- | --- |
| `POST /broadcast` | 受理指定接收方的异步任务分发 |
| `GET /broadcast/tasks/{task_id}` | 查询指定分发记录的进度和逐接收方结果 |
| `GET /broadcast/tasks/current` | 查询该源任务最近一次分发，包含运行中和已结束记录 |
| `PUT /dispatch-state` | 设置源任务及全部关联子任务的三态调度配置 |
| `GET /dispatch-state` | 查询调度状态、配置版本及平台同步进度 |

配套的 `/broadcast/children` 子任务查询已提出，详细契约另行梳理，不与分发请求或三态切换混为一个操作。

## 三个应用的职责

| 应用 | 负责 | 不负责 |
| --- | --- | --- |
| 智拓 | 选择接收方，设置散列选项，提交分发，保存 `task_id`，查询结果；按业务需要独立设置三态 | 不直接操作任务表、SWE CronManager 或平台定时器 |
| Scheduler | 分发校验和持久化，后台创建或更新子任务，调用 SWE 准备，保存结果，计算散列和必要的批入口时间，完成三态及平台同步 | 不接管整个财富规划，不把结果查询当作调度执行，不因状态切换取消既有队列 |
| SWE | 准备接收方执行环境、Chat、会话及路由；任务实际执行时直接保存运行状态 | 不分配分发记录，不替 Scheduler 写定义或分发、三态管理进度，不切换平台状态或同步 Monitor |

SWE、Monitor、Scheduler 使用同一个数据库。接口传递执行准备或执行操作，不重复 HTTP 同步同一份数据库任务数据。

## 异步分发接口

### 入参

```text
POST /api/scheduler/cron/jobs/{job_id}/broadcast
    ?scope_id=<源任务scope>&agent_id=<源任务Agent>
```

请求示例：

```json
{
  "request_id": "broadcast-request-001",
  "expected_definition_version": 3,
  "targets": [
    {
      "tenant_id": "sap1001",
      "tenant_name": "张三",
      "bbk_id": "001",
      "agent_id": "default"
    },
    {
      "tenant_id": "sap1002",
      "tenant_name": "李四",
      "bbk_id": "001",
      "agent_id": "default"
    }
  ],
  "enable_offset": true,
  "offset_window_hours": 4
}
```

| 字段 | 含义 |
| --- | --- |
| `request_id` | 同一次分发的稳定标识，超时重试必须复用；同一标识对应不同内容时冲突 |
| `expected_definition_version` | 期望的源任务定义版本，避免以过期源定义提交分发 |
| `targets` | 明确的接收方列表，当前智拓的 tenant 对应接收客户经理身份 |
| `tenant_name`、`bbk_id` | 目标身份补充和展示信息，不能替代服务端权限及归属校验 |
| `agent_id` | 目标 Agent；省略时沿用源 Agent 的默认方案，最终契约再确定 |
| `enable_offset` | 是否对接收方子任务进行散列错峰 |
| `offset_window_hours` | 散列窗口，用于计算各子任务偏移和最终排程 |

目标 source 继承源任务，scope 由服务端解析和校验，不让客户端通过任意 scope 绕过目标授权。目标列表需要规范化、去重，冲突身份信息拒绝处理。

请求不再包含 `enable_batch_dispatch` 或三态字段。客户端不能通过一次分发隐含切换历史接收方的模式。

Scheduler 从数据库读取源定义，智拓不重新传完整源任务。智拓当前使用无散列参数 `false`、`0`；上面的 `true`、`4` 示例用于展示散列能力，不改变智拓现有默认业务行为。

### 受理响应

校验通过并完成分发记录及目标明细持久化后返回 `202`，不等待全部子任务准备或平台同步完成。

```json
{
  "task_id": "distribution-001",
  "source_job_id": "source-job-001",
  "source_definition_version": 3,
  "status": "queued",
  "tenant_count": 2,
  "success_count": 0,
  "failed_count": 0,
  "pending_count": 2,
  "reused": false
}
```

`task_id` 是分发记录 ID，可以继续保存到智拓场景的 `broadcast_task_id` 中；不是定时任务实际执行的 `batch_id`。`202` 表示已持久化受理，不表示分发成功。

同一次请求重复提交返回同一个 `task_id` 和已有进度，不新增重复子任务，也不因查询或重复提交自动重跑失败项。业务失败由授权用户选择需处理的接收方，用新 `request_id` 发起新一轮分发；不另设旧轮续办接口，不新增后台自动业务失败重试。旧轮保留原结果和错误，新轮采用当前允许分发的源定义及本轮散列参数，不保证旧偏移不变。未选中的成功项不重复处理。

新轮仍需校验当前删除、权限、配置版本及模式协调约束；复用未删除子任务的身份和有效资源，核对未完成步骤，不因旧轮失败重复创建。平台操作结果不明时先核对已有绑定，不盲目重复注册。必要的批入口时间联动失败也应能由新轮根据全部当前有效子任务重算并收敛，不只重做目标创建。旧轮迟到工作不得覆盖新轮。

### 后台流程

1. 从数据库领取待处理分发，固定本次源定义版本及快照，记录目标、散列选项和偏移。不能只依赖进程内 `asyncio.create_task()` 及内存列表。
2. 为目标确定子任务身份。以源任务身份、目标 scope 和 Agent 查询关联子任务；已有未删除子任务走更新，没有子任务则预留新 ID 后走创建。
3. 构造目标执行定义，继承源任务内容、技能和排程，替换目标身份和执行用户，保存源子关联。不复制源任务的 Chat、会话、外部定时器 ID、未读及执行结果。
4. 读取并协调源任务已生效的调度状态：两种批状态均生成批子任务；普通状态生成普通子任务。先确定模式，再调用保存和平台处理能力，批子任务不先注册普通定时器再停用。
5. 复用 Scheduler 内部创建或更新服务，调用 SWE 准备目标执行资源，保存定义、状态、旧表投影及对应模式需要的平台同步结果。
6. 更新已有子任务时，内容、模型、技能及排程重新按源定义生成，接收人此前对这些内容的修改会被本次明确分发覆盖；保留它自己的 ID、Chat、会话、启停及运行结果。与正在发生的独立编辑以版本校验保护，冲突明确报告。SWE 准备能力对缺失的指定模型回退接收方默认模型并告警；必要 Workflow/技能配置缺失则该接收方失败，不能虚报准备成功。默认模型本身不可用时同样不能视为成功。
7. 新任务只保存数据库定义和状态，不投递文件或旧内存兼容操作。
8. 逐接收方保存进度、结果、错误和警告，采用有上限的并发。一人失败不撤销其他已成功任务。
9. 根据全部有效关联子任务排程，完成必要的批入口时间联动；不由此开启或关闭批模式，也不能把暂停的入口打开。
10. 保存整体汇总结果，供智拓查询。必要联动失败应明确暴露，不能把局部成功包装成全部完成。

明确的新一轮分发再次包含曾删除子任务的接收方时，预留新的子任务 ID，旧记录保持已删除；新旧资源、绑定及清理隔离。新分发重试复用自身已保存的目标身份，不重复创建。旧分发重试或迟到工作不能因原子任务已删除而复活原任务或另建替代任务。

后台应具备数据库领取和恢复机制，避免多实例重复处理；实例退出后可从已保存的原轮进度继续并复用原快照及偏移。这种中断恢复不等于对已确认业务失败自动重试。领取、租约和接口数量限制在实现前细化。

## 散列参数的归属和处理

散列属于分发时子任务排程的生成规则，由 `POST /broadcast` 的 `enable_offset`、`offset_window_hours` 控制。

Scheduler 计算并持久化每个目标的 `offset_minutes`、最终 Cron 和时区。同一次分发重试复用已确定的偏移，不因处理顺序改变或实例重启重新散列。

已确认沿用现有算法：按本轮规范化后的目标顺序，在 0～24 小时窗口内均匀计算偏移，并将 Cron 向前平移；不是租户哈希随机散列。新一轮目标顺序或人数不同可能改变同一接收方的偏移，实例重启恢复原轮时则复用原偏移。

结果查询返回实际应用的偏移、Cron、时区和警告。已确认保留旧回退：Cron 无法安全平移时使用原 Cron 和时区，实际偏移为 0，逐目标记录警告；不因此单独判分发失败，也不能声称已成功应用请求的散列。通知计算使用实际排程及实际偏移，不使用未应用的请求偏移。

### 0 人分发：只调整既有子任务散列

`targets` 为空时，从数据库固定该源任务全部未删除关联子任务的目标集合和必要版本，包括停用子任务；按稳定顺序重算排程、散列及必要平台联动。不覆盖正文、模型和技能，不重新复制源定义内容，不恢复启用，不创建子任务、Chat 或会话。没有关联对象时不创建任务，查询结果应准确反映没有处理对象。

0 人调整同样异步并记录逐项进度，遵守同源分发串行及并发版本保护，必要的排程更新沿用更新门禁。含目标的普通分发只处理本轮指定接收方，不借调整散列扩散更新全部历史对象。

暂停批调度保留散列配置；切回普通调度时，各任务使用数据库中已有的错峰排程，不重新计算散列、不重新分发。

旧代码同名窗口参数还用于批父入口提前时间。拆分后，客户端只在分发接口设置散列；Scheduler 根据全部有效关联子任务的排程计算、同步批入口时间，不再要求三态接口重复传窗口。部分接收方重新分发时，也要考虑未包含在本次 targets 中的既有子任务排程。

## 分发结果查询接口

### 查询指定分发

```text
GET /api/scheduler/cron/jobs/{job_id}/broadcast/tasks/{task_id}
    ?scope_id=<源任务scope>&agent_id=<源任务Agent>
```

查询持久化分发记录，返回源任务身份和版本、状态、数量统计及逐接收方结果。建议状态语义为排队、处理中、全部成功、部分失败、全部失败；对应枚举及现有状态适配在实现时确定。

结果示例：

```json
{
  "task_id": "distribution-001",
  "source_job_id": "source-job-001",
  "source_definition_version": 3,
  "status": "partial_failed",
  "tenant_count": 2,
  "success_count": 1,
  "failed_count": 1,
  "pending_count": 0,
  "results": [
    {
      "tenant_id": "sap1001",
      "agent_id": "default",
      "job_id": "child-job-001",
      "operation": "created",
      "status": "succeeded",
      "cron": "0 9 * * *",
      "timezone": "Asia/Shanghai",
      "offset_minutes": 0,
      "error_code": null,
      "error": null,
      "warning": null
    },
    {
      "tenant_id": "sap1002",
      "agent_id": "default",
      "job_id": "child-job-002",
      "operation": "created",
      "status": "failed",
      "cron": "0 5 * * *",

```

例子表示原排程为每天 09:00，两个目标使用四小时窗口得到 0 和 240 分钟的提前偏移。失败对象可以已经有预留任务 ID，不表示它已具备执行条件。

`succeeded` 表示子任务创建或更新的必要准备和同步完成，不表示 Agent 已执行成功，不涉及文件或旧内存兼容完成状态。查询不改变调度状态，不查询执行历史。

查询需要校验分发记录确实属于指定源任务。创建人或管理者按授权看整体结果；如保留接收人视角，只能返回该接收人有权看到的结果，不暴露其他用户的数据。

### 查询最近一次分发

```text
GET /api/scheduler/cron/jobs/{job_id}/broadcast/tasks/current
    ?scope_id=<源任务scope>&agent_id=<源任务Agent>
```

这是必需接口。按指定源任务身份返回最近一次分发，包含排队、处理中和已结束记录，不只查当前运行中的记录。应按分发创建顺序确定最新记录，避免旧请求晚完成后变成 current。

有记录时返回：

```json
{
  "task": {
    "task_id": "distribution-001",
    "status": "queued",
    "tenant_count": 2,
    "success_count": 0,
    "failed_count": 0,
    "pending_count": 2,
    "results": []
  }
}
```

没有记录时返回：

```json
{
  "task": null
}
```

记录缺失不能视为分发成功。显式查询不存在的 `task_id` 应返回明确的不存在结果；具体错误契约待细化。实现路由时静态 `current` 路径应避免被动态 `{task_id}` 路径误匹配。

## 三态切换接口

### 设置调度状态

```text
PUT /api/scheduler/cron/jobs/{job_id}/dispatch-state
    ?scope_id=<源任务scope>&agent_id=<源任务Agent>
```

请求示例：

```json
{
  "state": "batch_paused",
  "expected_version": 3
}
```

`expected_version` 校验三态配置的并发修改。它与任务定义版本的具体对应和存储字段在表设计时细化，不应被未读次数等无关运行状态变化混淆。

接口不接受 `enable_offset`、`offset_window_hours`，不重新分发、不重新计算子任务散列，也不重新准备 Chat 和会话。

| 调度状态 | 批平台入口 | 后续新任务触发方式 |
| --- | --- | --- |
| `batch_enabled` 开启批调度 | 开启 | Scheduler 接收新的批触发并按批任务流程入队派发，子任务不启用独立普通定时器 |
| `batch_paused` 暂停批调度 | 关闭 | 保留批模式及父子关系，不切回普通调度，也不启用子任务普通定时器 |
| `ordinary` 普通调度 | 关闭 | 源任务和子任务按各自启用状态使用普通定时器 |

三态不同于单个任务自身的 `enabled`。切换模式不能把用户暂停的子任务无条件恢复为启用。

### 状态切换范围和动作

三态属于源任务及其全部有效关联子任务这一组，不仅本次分发 targets。Scheduler 从数据库查询关联关系，不扫描所有用户的 `jobs.json`。

| 转换 | 动作 |
| --- | --- |
| 开启批调度 → 暂停批调度 | 关闭批平台入口，保留批模式、关联关系和定时器 ID |
| 暂停批调度 → 开启批调度 | 开启对应批入口，不重新分发和新建子任务 |
| 任一批状态 → 普通调度 | 关闭批入口，关联任务切回普通模式，按各自启用状态更新或恢复普通定时器 |
| 普通调度 → 开启批调度 | 停用关联普通定时器，切为批模式，准备并开启批入口 |
| 普通调度 → 暂停批调度 | 停用关联普通定时器，切为批模式，保持批入口关闭 |
| 重复设置相同状态 | 幂等处理，不重复注册；若此前同步未完成，继续收敛未完成事项 |

批子任务此前没有普通定时器时，切回普通模式需要注册；已有普通 ID 则复用。模式切换导致的必要注册不等于更新接口无故重复注册。

例如第一次分发 A、B、C，后来仅向 A、D 重新分发：重新分发只处理 A、D；独立模式切换则作用于 A、B、C、D 的全部关联任务。它不会删除未在本次 targets 中的 B、C。

### 切换内部流程及结果

三态切换采用异步处理：持久化操作目标和进度后返回受理事实，后台处理平台同步，客户端查询当前操作进度。当前切换未完成时，不接受另一个不同目标；相同目标请求按操作身份复用，失败时允许人工重试未完成步骤，不重做成功项。精确响应字段与重试契约在接口契约中整理。

1. 校验源任务、操作权限和三态配置版本，记录目标状态及同步进度。
2. 查询全部有效关联子任务，协调新平台触发入口和各任务的调度方式。
3. 保存任务定义和状态变化，完成普通及批定时器的必要注册、更新和启停，并记录结果。
4. 更新旧表兼容投影，不向 SWE 投递文件或旧内存刷新。三态切换不调用 SWE 的旧任务保存或平台注册逻辑。
5. 返回业务状态、版本及平台同步进度。部分定时器失败时记录待处理事项，不能只报告整组已完成。

已确认：外部处理失败只提示并支持人工重试未完成步骤，保留成功项和目标，不自动回滚、不新增自动业务失败续办；不能仅因平台同步待处理或失败而阻止整组触发。平台操作结果不明先核对，不盲目重复注册。实际停用、删除、暂停批调度、权限及去重规则仍有效，已有队列与运行不受同步失败影响。

三态状态和平台同步进度是不同信息。状态接口的响应示例：

```json
{
  "job_id": "source-job-001",
  "state": "batch_paused",
  "version": 4,
  "sync_status": "completed",
  "error": null
}
```

已确认普通与批模式部分切换成功时允许逐对象临时混合：成功对象按新方式，未同步对象暂按原方式继续，人工重试后统一；暂停批调度、单任务停用和删除仍按数据库业务状态生效。目标模式、各对象生效方式及同步进度分别展示，不能以整组三态枚举隐藏局部失败。普通/批入口校验各对象的有效平台绑定并按同一逻辑执行期去重，避免该对象被两种方式各执行一次。此处原方式不是存量老接口，两种方式均在本次新任务通道内。

### 查询调度状态

```text
GET /api/scheduler/cron/jobs/{job_id}/dispatch-state
    ?scope_id=<源任务scope>&agent_id=<源任务Agent>
```

从数据库返回三态配置、版本、平台同步进度和错误或待处理事项。查询不主动开启平台入口，不以文件内容或一次远程调用成功替代整组同步结果。

## 已有执行队列继续运行

三态切换只控制后续新触发，不追溯干预已接收的执行工作：

- 已入队的批执行任务继续被 Scheduler 派发，不取消、不清空。
- 正在执行的任务正常结束，不取消、不重启；结果仍可正常记录。
- 暂停批调度只是关闭平台批入口，不暂停已有队列的消费。
- 切回普通调度后，已有批队列继续完成，后续新触发按普通模式处理。
- 旧队列不得仅因当前模式变化、批入口关闭而被拒绝；后续完成回写也不得恢复旧模式。

实现时必须区分新批次接入门禁和已有队列消费门禁，不能用一个暂停条件同时挡住两者。保留入队执行身份和必要快照，并做好新旧入口间的去重、并发控制，避免同一次执行被重复提交。

以上约定只针对三态切换，不修改单任务删除及独立权限校验规则。分发后台队列和定时任务执行队列是不同队列，不应把“执行队列继续”解释成分发后台可以忽略任务删除或所有版本冲突。

## 分发与模式切换的并发协调

同一完整源任务身份（tenant/source/Agent/源任务 ID）一次只允许一轮分发排队或处理中。另一轮新请求不受理并返回当前分发 ID 和进度；同次请求幂等重提仍返回原分发，不推进旧失败项。由数据库协调多实例并发受理和领取，不能只禁用按钮或依赖进程内锁；实例退出后待恢复的非终态分发仍属于进行中。历史失败通过新一轮重试，不设置旧轮续办接口，旧轮迟到工作不能覆盖新轮。

分发不再指定目标模式，但后台创建子任务仍要匹配源任务已生效的模式。应使用配置版本校验或操作互斥，不让一次后台处理生成无法收敛的混合模式任务。

受理时固定源执行定义快照和散列偏移。处理期间的三态变化需要协调，使晚到的子任务和平台更新不会恢复过时模式；不能因为分发记录保存了旧模式就无条件按旧模式新建定时器。

模式切换、分发和散列导致的批入口时间调整也需要共同检查版本及启停状态。只更新入口排程不能把 `batch_paused` 重新变成 `batch_enabled`。

已确认源任务在仍有未删除子任务或分发尚未结束时不允许修改内容；停用子任务仍算存在。子任务全部逻辑删除且分发结束后允许再修改，不因历史分发永久锁定。独立启停、三态和优先级不受该内容限制。分发排队或处理中拒绝源任务删除，返回当前分发进度，结束后才允许重试；拒绝时不写删除标记或清理资源。删除与分发受理必须在数据库内协调，不能仅靠按钮。子任务独立编辑用版本冲突保护；同一次分发不能混用源定义版本、复活已删除任务或覆盖并发执行结果。

## 数据持久化

| 对象 | 归属和作用 |
| --- | --- |
| `swe_cron_jobs_v2` | Scheduler 保存源子关系、完整子任务定义及最终排程 |
| `swe_cron_job_states` | Scheduler 初始化子任务状态并保存准备绑定、平台注册及管理进度；实际执行产生的运行状态由 SWE 直接写入 |
| `swe_cron_jobs` | Scheduler 维护新任务的旧表兼容投影，不修改 SWE、Monitor 原有旧写入逻辑 |
| `swe_cron_broadcast_tasks`、`swe_cron_broadcast_task_items` | 作为分发进度和逐目标结果的复用方案，需补齐请求标识、快照、scope/Agent、领取恢复及约束 |
| 平台操作日志 | 可复用此前 `swe_cron_registration_journal` 设计，具体扩展待细化 |
| 三态配置 | 具体表、字段及配置版本存储待细化，明确唯一权威位置，避免两处互相覆盖 |
| `jobs.json` / SWE 旧内存 | 新任务不补写，也不作为新路径读取来源 |

每个接收方复用创建、更新流程的数据库写入顺序。分发汇总及明细由 Scheduler 直接持久化，查询不依赖后台进程内存。

分发处理进度、调度三态和任务实际运行状态分别维护。Scheduler 改三态时不重置 SWE 的运行结果，SWE 保存执行结果时不恢复旧模式。执行结果共库只保存一份，Scheduler 据此维护自己的执行队列和批次；字段归属及并发规则见 [执行状态写入分工](2026-10-14-zhituo-scheduler-cron-execution-entry-flow.md#执行状态写入分工与并发约束)。

接收方任务、三态和分发进度均以数据库为准，不建立文件或旧内存兼容投影。新任务切普通后使用 Scheduler 新普通回调，不回到旧 SWE 文件执行通道。

分发和三态操作按完整任务身份、版本和删除状态处理迟到结果，不能覆盖新定义、恢复已删除任务或重新接管到旧 SWE 路径。

## 新管理页配套能力

批调度配置需支持优先用户、优先支行及其顺序的读取和保存，复用既有优先算法，按新任务数据库及执行快照适配。策略只对后续新批次生效，不增加分发接收人，不重排既有批次。它与源任务内容更新和三态切换分别管理，最终版本及权限契约待澄清。

子任务列表的批量删除与批量立即执行纳入第二阶段，优先复用单任务接口组合；不把源任务单次删除解释为自动级联，也不把刷新列表解释为再次分发。逐项授权、部分成功、重复提交和在途任务行为需在完整澄清中确认。

## 实现前需要细化的内容

- 接口鉴权、目标授权、请求字段类型、默认值、数量上限及精确错误码。
- 请求幂等约束、源快照和目标偏移保存方式，以及分发记录与预留子任务 ID 的持久化映射。
- 分发后台的多实例领取、租约、中断恢复和跨轮版本保护；业务失败通过新一轮重试、不另设旧轮续办接口已确认。
- 分发结果状态和计数口径，旧智拓看板状态如何适配。
- 三态配置存储、版本及业务目标、生效状态、平台同步状态的响应契约。
- 三态切换与后台分发、内容更新、散列窗口调整之间的并发顺序。
- 普通和批入口切换时的执行去重，以及旧队列如何继续派发而不被当前模式门禁拒绝。
- 已确认的散列算法、Cron 回退告警、0 人仅调整排程的契约及批入口时间自动计算边界；不再重复选择算法或回退策略。
- 分发查询的创建人及接收人权限，源任务删除后的历史结果可见性。
- `/broadcast/children` 的详细查询契约，另行梳理。
