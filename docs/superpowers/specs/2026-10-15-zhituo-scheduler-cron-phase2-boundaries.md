# 第二阶段：Scheduler 新任务的数据库链路边界

日期：2026-10-15。状态：业务边界已确认，第二阶段实现中。已实现范围及剩余工作见[开发进度](../plans/2026-10-15-scheduler-cron-phase2-progress.md)，不能据此认为全部业务代码已完成。本文件对同目录原有流程文档的以下约定进行统一修订。

## 新旧任务按管理归属区分

- 新任务：通过 Scheduler 新创建接口建立、归 Scheduler 管理的任务，以及分发创建的子任务。
- 存量任务：继续由原 SWE 路径管理的任务。第一阶段将其定义和可恢复状态导入数据库，只建立快照，不自动转交管理权。
- 不按创建日期区分新旧，也不以“新表里有记录”直接判定已经接管。智拓对接仍属于第三阶段。

本文件及配套新流程文档只约束新增接口和 Scheduler 管理的新任务通道。存量管理、执行、平台入口及协议保持原行为；复用公共代码不构成改变老接口语义的授权。

## 2026-10-19 平台回调最新确认

平台只发送 tenant_id/source_id/agent_id/job_id/task_type/scopeId/fromId/callback_protocol/operation_id，不提供 Header、平台任务 ID、执行流水号或触发时间。新版普通/批回调均支持这一平铺 Body，也兼容原 jobParam 编码封装。身份和有效注册操作引用仍须核对共库；Header 存在时保留冲突检查，不能从 Body 提升管理角色，沿用可信内网平台入口边界。

用户明确“不需要去重，每次都视为是有效的”：每次回调独立生成回执和执行/批次，不按流水号、计划期或普通/批入口合并。缺时间使用接收时间作为物理触发时间，加已保存提前量作为逻辑时间。2026-10-19后续修订：批入口提前触发后整批成员在受理时间统一就绪，不再按各自散列偏移等待；仍按冻结优先级、热度和共享容量派发。普通调度和原通知逻辑期不变。实际停用、删除、暂停批调度、管理就绪、定义版本及归属校验不取消。仅对同一次已入队执行保留内部派发、结果和恢复幂等；管理请求号幂等不变。本节覆盖原流程文档中的平台重复触发不执行、稳定日志/计划时间必填及跨入口周期去重约定，也覆盖早期“批内散列成员等待”的描述。历史批次快照不自动回填。

## 取消文件及旧内存兼容

新任务的创建、修改、删除、分发、三态切换和执行不补写 jobs.json，也不向 SWE 旧任务内存 _states 补展示投影。不开发兼容文件写入器、旧内存适配层、兼容刷新接口及相关补偿机制。

新任务查询直接使用 Scheduler 的数据库查询，不为旧 SWE 查询增加查库回填。旧接口本身不包含新任务；前端按下节另行查询并合并展示。存量文件、内存和旧查询逻辑不删除、不统一重构。

执行所需的信号量、锁、在途对象和请求上下文仍保留。Chat、会话和执行产物的现有存储不属于本次全部文件数据库化。

本次取消仅限文件与旧内存。此前确认的新任务 swe_cron_jobs 数据库兼容投影暂时保留，SWE/Monitor 原有旧任务写入逻辑不动。

## SWE 前端新旧任务共存

- 保留旧定时任务管理页，新增“定时任务（新）”页，新页只管理 Scheduler 创建的任务；不把导入的新表 legacy 快照误当作已接管任务。
- Chat 页面保留旧列表请求，额外调用 Scheduler 新任务列表接口，按旧任务在前、新任务在后合并。新任务需要转换为任务栏所需的运行状态、未读和 Chat 绑定视图，不把原始表记录直接当作完整展示对象。
- 任务会话有效性过滤同时参考两份列表。某个列表请求失败不能将该来源任务判作已删除；新任务分页不得只取第一页就当作完整存在性清单。
- 前端保存任务来源/管理归属，编辑、删除、暂停恢复、立即执行和标记已读按归属分流；新接口失败不自动回退旧写接口。服务端仍按完整身份与真实归属鉴权，不能信任客户端标记代替校验。
- 结果预览沿用原有内容读取和展示能力。携带 CRON_JOB_ID 的预览在标记已读时，旧任务调用旧接口，新任务调用 Scheduler 新接口更新数据库已读状态；不补写文件或旧内存。

报告预览只有任务 ID 时，需结合可信的 tenant/source/Agent 上下文确认任务归属；不能因为新表中有快照就判为新任务，也不能通过“先尝试一个写接口、失败后换另一个”探测归属。新接口的路径、视图模型、已读事务及并发执行新增未读的处理仍在契约设计时细化。

## 新页面完整功能覆盖要求

2026-10-19 异步删除补充：新版选中子任务删除及删除全部均先固定确认快照并持久受理，再由Scheduler后台逐项处理；返回202不等于逻辑删除完成。关闭页面不取消已受理清单，重新打开查询当前删除进度。全部删除不再依赖前端1000项分片等待；选中删除单次仍最多1000项。查询只读；整批意外中断人工重新排队，单项清理业务失败继续用其原操作人工续办。同源分发与处理中的删除互斥、在途执行继续等原边界不变。本节覆盖早期文档中“同步批量删除、关闭后停止下一片”的约定。

以下能力已确认纳入第二阶段，不再作为可选的后续功能；具体契约和业务边界按[完整澄清清单](2026-10-15-zhituo-scheduler-cron-phase2-clarification.md)逐项确定。

| 能力 | 本阶段要求 |
| --- | --- |
| 单任务启用、停用、恢复 | 独立于内容更新及整组三态，只控制指定任务自身；停用跳过尚未开始的排队执行，已开始的继续完成，其他任务不受影响 |
| 立即执行 | 不冒用平台回调；停用时拒绝并要求先恢复，运行中拒绝新的手动触发；已有待开始的手动请求时不重复创建，返回原请求进度，同一次请求重试保持幂等 |
| 批调度优先级 | 支持优先用户和支行的读取、保存及排序，复用既有优先算法；仅影响后续新批次，不修改接收人或既有批次快照 |
| 子任务批量操作 | 支持选中子任务的批量删除、批量立即执行，返回逐项结果；优先复用单任务接口组合，不默认新增批量后台系统 |
| 新任务列表与 Chat 展示 | 提供分页、筛选、完整管理归属和展示视图，支持新管理页及新旧列表合并 |
| 标记已读 | 新旧归属分流，新接口正确协调 SWE 并发新增未读，不隐式恢复停用任务 |
| 管理进度与安全重试 | 详情区分准备、平台同步、更新待处理、删除待清理等事实；明确同一次操作重试与新操作的边界 |

恢复任务时沿用既有行为，将恢复操作当时已有的未读结果标为已读，历史内容保留；之后新结果仍计为未读。恢复自身不能解除更新未完成、删除或整组三态的独立门禁，标记已读本身也不会隐式恢复任务。

2026-10-19 补充：Scheduler 新任务的手动成功结果与自动成功结果一样更新展示和未读，历史仍保留 is_manual=1，不预设已读；复用已有标读接口。为兼容接口字段名，has_scheduled_result/latest_scheduled_preview/last_scheduled_run_at 在新版通道包含手动成功结果。手动结果不直接触发自动未读暂停，通知规则不变。Chat 对新任务优先展示 state.last_run_at 与实际状态，已有运行时间即不再提示尚未启动；旧任务行为不变，历史已读记录不回填为未读。

子任务刷新直接重新查询数据库，不照搬原来的全用户文件扫描和异步列表快照构建。分发、三态查询已有设计；前端按新职责拆分交互，不增加重复控制接口。技能、模型、租户选择及报告内容读取等公共能力继续复用。

创建、更新使用同步主流程，等待必要的 SWE 准备和平台同步完成后返回；异常保留已保存进度与同次操作身份，由用户人工重试续办，不新增后台自动业务续办，不因 HTTP 超时重建任务。2026-10-17确认平台没有注册查询接口：未取得已保存平台ID按注册失败处理，原操作人工重试可以再次新增，可能遗留重复/孤立定时器；已有ID则始终复用。分发仍异步；部分失败由人工选择接收方发起新一轮分发重试，不单独开发旧轮续办接口，不新增后台自动业务失败重试。新轮使用当前源定义及本轮散列参数，复用未删除子任务和有效资源，不重建已存在对象，旧轮保留查询。服务重启后的原轮进度恢复仍需支持，执行派发恢复另行确定；执行请求返回受理事实，不等待实际运行完成。

源任务存在未删除子任务或分发仍在进行时，不允许修改其内容；停用但未删除的子任务仍算存在。子任务全部逻辑删除且分发结束后允许再次修改，不因历史分发记录永久锁定。独立启停、三态和优先级不受该内容编辑限制，服务端需协调检查与并发分发，不能只靠前端按钮控制。

删除后平台停用或 SWE 资源清理失败，保留“已删除、清理未完成”的可查询记录，由授权用户人工重试未完成步骤，不自动后台失败续办、不恢复任务。新管理页需保留对应查看和重试入口，不能删除后立即丢失操作对象。正常等待在途执行结束的资源延后清理不等于清理失败。

明确的新一轮分发再次包含曾删除子任务的接收方时，创建新 ID 的子任务，旧记录保持已删除；新旧资源、绑定及清理隔离。旧分发重试或迟到工作不得复活原任务或另建替代任务。

同一完整源任务身份一次只允许一轮分发排队或处理中；新一轮并发请求不受理，返回当前分发 ID 和进度。同次请求幂等重提不算另一轮，也不自动重跑失败项。由数据库协调多实例受理及恢复，不仅依靠前端按钮或进程内锁。历史失败轮不另行续办，通过新一轮重试；旧轮迟到工作不得覆盖新轮。

分发继续采用按本轮目标顺序均匀提前的散列算法，窗口 0～24 小时；Cron 无法安全平移时保留旧回退，实际使用原排程、偏移 0，并告警，不虚报已应用散列。0 人模式仅重算全部未删除关联子任务（包含停用对象）的排程及必要平台联动，不覆盖正文、不恢复启用、不创建任务。

再次分发按源定义更新内容、模型、技能和排程，但保留子任务 ID、Chat、会话、启停及运行结果，并校验并发编辑版本。指定模型缺失时回退接收方默认模型并告警；必要 Workflow/技能配置缺失则该接收方失败，其他人继续。分发排队或处理中拒绝源任务删除，返回当前进度，等待分发结束后重试；拒绝时不写删除标记或清理资源，受理与删除在数据库内协调。

## 普通与批调度均使用新入口

| 管理归属与模式 | 平台入口与执行路径 |
| --- | --- |
| Scheduler 普通任务，包括新任务切普通 | 平台 → Scheduler /api/scheduler/cron/ordinary/callback → 数据库定义与执行快照 → SWE 新执行接口 |
| Scheduler 批任务 | 平台 → Scheduler /api/scheduler/cron/batch/callback → 新执行批次、队列与快照 → SWE 新执行接口 |
| 存量普通及批任务 | 原平台 URL、协议、文件与内存逻辑不变 |

不再保留“新版普通先开发不用”或“新任务切普通后交回 SWE 文件入口”的约定。仍由外部平台负责时间触发，Scheduler 不新增扫描全部普通任务判断到期的循环。

## 更新期间的新触发门禁

本节针对内容更新准备及版本生效，不适用于单纯三态外部同步失败。三态按下节最新规则，不因平台同步未完成增加整组触发阻断。

更新期间暂缓接收新触发；已入队或正在执行的任务按原快照继续，不取消、不重启。新配置先作为待生效版本，SWE 准备和平台同步均确认完成后才发布，并且仅按任务原本允许的启用条件解除更新门禁。

失败保留待处理状态与新触发门禁，允许复用同一次操作安全重试，不把未确认结果当作更新成功。管理门禁不等于重置用户 enabled、三态或已有运行结果。

已确认：更新期间到达并被暂缓受理的触发不补跑，记录原因；更新完成后等待下一次回调。按 2026-10-19 约定，后续收到的任何回调均作为独立新请求校验，不复用或补跑先前跳过记录。

## 三态外部处理失败不阻断触发

外部处理失败提示错误并支持人工重试未完成步骤，保留目标及逐项进度，不自动回滚、不新增自动业务失败续办，也不因平台同步待处理或失败增加整组触发阻断。已保存平台ID的成功项不重复操作；没有已保存ID则按注册失败，原操作人工重试允许再次新增，可能留下重复定时器；查询不得虚报平台已同步完成。

不阻断触发不表示忽略实际停用、删除、暂停批调度及权限校验。已有队列和运行继续。三态切换异步受理；普通与批部分切换成功时允许逐对象临时混合，成功对象按新方式，未同步对象暂按原方式，重试后统一；按 2026-10-19 约定，平台每次回调独立受理，不做跨入口周期去重。切换未完成不接受另一个目标模式，只允许查询和重试原切换。内容更新准备及版本生效规则保持原约定，不因本条自动取消。

## 权限及执行失败边界

前端及智拓管理接口沿用可信身份 Header 和既有权限体系；平台回调按本文件最新确认支持 Body 身份。有权管理源任务的调用方可管理关联子任务及整体分发结果；接收方仅管理自己的子任务，不操作其他接收方或源任务，不新建角色体系。

Agent/Workflow 已实际执行失败时记录失败，不自动重跑本次业务执行；可人工立即执行或等待下次排程，仍遵守启停和并发约束。SWE 按本次执行身份直接写共库受理/开始和最终结果，Scheduler 读表确认，不等待 HTTP 执行完成回执，不要求完成回调重复搬运结果。触发请求的快速受理响应不等于运行结果；响应丢失时查共库、按原执行身份幂等恢复，不据此新建一次业务执行。长期异常判定和恢复作为技术契约细化，不新增未经批准的人工核对功能。

服务恢复只续办已持久受理的执行和队列，不扫描全部任务定义补生停机期间未收到的触发。平台重新发送回调按独立新请求处理；同一执行在服务内部恢复仍使用原 execution_id，不重新运行已发生业务。

## 保持不变的约定

- SWE、Scheduler、Monitor 使用同一个数据库。
- Scheduler 写定义、准备绑定、平台管理和删除等管理字段；SWE 直接写实际运行状态及结果，不经 HTTP 重复保存同一份状态。
- 分发保持异步、0～1000 人，散列参数仍属于分发接口；指定及 current 分发查询保留。
- 三态切换不取消已入队或执行中的任务。删除仍阻止未开始任务，已开始执行可完成。
- 新普通和批执行都覆盖 Agent、文本和 Workflow，执行结果幂等、版本及迟到回写约束保持。
