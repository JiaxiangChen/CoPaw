# 第一阶段定时任务快照迁移 Postman 操作说明

第一阶段只将用户任务定义和可恢复状态写入 `swe_cron_jobs_v2`、`swe_cron_job_states`。不切换前端、CRUD、执行入口或平台定时器，不增加日常双写，不迁移心跳、梦境、清理、归档等独立系统任务。

## 推荐：一次提交全量迁移

无需再手工反复提交下一页。新增异步入口会在收到请求的 SWE 实例后台自动翻页，查询可以命中其他实例。

除两张业务目标表外，异步进度复用已有 `swe_async_tasks`、`swe_async_task_items`；这两张既有表必须存在且结构兼容。无需新增迁移任务表或修改列，应用不会自动建表；若尚未部署，可由操作者检查仓库已有 [async_task_tables.sql](../../scripts/sql/async_task_tables.sql) 后手工部署。原同步分页能力不依赖这两张进度表。

### 1. 提交全量预检

`POST {{swe_base_url}}/api/internal/cron/migration/tasks`

```json
{"operation": "preview"}
```

沿用下文已有认证和路由 Header。省略身份筛选表示扫描当前服务可见的全部 source、用户和 Agent；不含独立系统任务。提交立即返回 HTTP 202 和 `task_id`，不必等全部扫描完成。异步预检/核对不改业务数据，但会写异步进度表；需要完全只读时使用原同步 `/preview`、`/verify`。

### 2. 查询累计进度

`GET {{swe_base_url}}/api/internal/cron/migration/tasks/{{task_id}}`

关注 `status`、`progress.counts`、`progress.pages_completed`、`progress.scan_complete`、`progress.partial_failure`、`progress.memory_incomplete` 和 `error`。查询只读，不会驱动下一批迁移，不要求命中执行实例。

| status | 含义 |
| --- | --- |
| queued / running | 等待开始 / 自动分批处理中 |
| succeeded | 本轮扫描结束且没有已识别的失败/冲突；仍要检查内存缺失与业务诊断，不等于集群内存全齐 |
| partial_failed | 已扫描结束，但有失败/冲突；核对时的 missing、different、source_missing 等也计入此状态 |
| failed | 后台异常、来源变化或单页超时等导致本轮没有正常结束，查看安全错误码 |
| stopping / stopped | 已请求停止 / 已在批次边界停止，成功提交的记录保留 |
| interrupted | worker 被取消，或超过 120 秒没有可确认的心跳；后者是疑似中断，不等于已确认旧 worker 完全停止 |

`counts` 在异步查询中是已完成批次的累计数。`scanned_files` 是各批次扫描次数之和，可能重复计算同一文件，不是不同文件数；不提供虚假的总任务百分比。当前批次已提交但尚未写进度时，计数可能暂时落后于业务表。

`pages` 保存完整的逐页安全诊断，默认返回前 10 页。需要看后续明细时，用响应中的 `next_after_page` 作为查询参数 `after_page`；`limit` 控制返回结果页数（1～20），不是控制后台迁移。这里只是读取诊断，迁移不会等待你查完结果。

例如 `GET .../tasks/{{task_id}}?after_page=10&limit=10`。运行期间可重复查询，累计进度不随明细页切换。

### 3. 正式全量导入

预检诊断确认后，再向同一 `/tasks` 地址提交：

```json
{"operation": "import"}
```

每次提交生成新的 `task_id`，后台从头扫描；无需传 `cursor`。`limit` 可选（默认 50，上限 200），仅控制后台单批大小，不限制迁移总量。也支持原有 `tenant_ids`、`source_ids`、`agent_ids`、`job_ids` 筛选用于小范围演练和补迁。

### 4. 全量核对

```json
{"operation": "verify"}
```

仍提交到 `/tasks`，后台自动完成来源和数据库两段核对；查询该任务直到终态。只有 `scan_complete=true` 才表示扫描自然完成，不能只看 HTTP 202/200。任务源仍可能被旧流程修改，核对不是停机一致性切换。

### 停止、重启与重跑

`POST {{swe_base_url}}/api/internal/cron/migration/tasks/{{task_id}}/stop`

不用正文。请求停止后，当前批次继续结束，在下一批开始前停止；已提交数据不撤销。不同实例也可以提交停止请求。原同步分页请求不受这个停止接口控制。

目前后台 worker 不自动跨实例接管或在重启后续跑。实例退出、异常失败或来源改变后，保留旧任务进度，重新提交同一范围即可安全重跑；不需要复制游标，不重复建业务任务。疑似中断时先确认实例/数据库是否恢复，必要时请求旧任务停止并确认，不把心跳过期当作确认取消。

执行实例每 15 秒写一次心跳，单页保护超时为 300 秒，单进程最多同时执行两个迁移任务；超额提交返回 429。来源文件 8 MiB、来源清单 20,000 文件等既有保护上限保持，超过时报错，不宣称已迁全量。

文件“全量”仍只指该实例可见的挂载目录。内存只采集执行实例实际已加载的状态，不能一次请求读到其他实例内存；按用户路由补迁方法见下文。后台不新增日常同步，不启动 Workspace。

以下保留同步分页接口说明，适用于抽样检查、无异步进度表时操作及问题定位，不是全量操作的必经步骤。

## 上线前

1. 由操作者手工执行准备阶段交付的两张目标表建表语句。不要为第一阶段执行分发/队列 ALTER，执行历史表不需要新增字段。
2. 确认 SWE 使用已有共用数据库连接。缺库、缺表或结构不兼容时接口返回不可用，不自动建表。
3. 备份或抽样记录原 `jobs.json`，记录旧任务数量、启停状态、平台定时器 ID 与一次正常执行结果。
4. 将 `/api/internal/cron/migration/` 限制在可信运维网络或网关规则内，不能当普通前端开放接口。用户信息 Header 是路由信息，不是跨用户迁移权限凭据。

应用回退只需回退本次代码或停止调用接口，不删除新表、不把新表写回旧文件或旧表。

## 请求地址与 Header

以 `{{swe_base_url}}` 表示 SWE 网关地址；原有三个同步接口都是 `POST`：

- `/api/internal/cron/migration/preview`：只读预检。
- `/api/internal/cron/migration/import`：写入快照。
- `/api/internal/cron/migration/verify`：只读对照，不修复。

Header 使用已有环境约定：

- `Content-Type: application/json`。
- `X-Tenant-Id`、`X-Source-Id` 等已有用户路由 Header，用于命中对应 SWE 实例。
- 仅在现有登录认证已开启时提供 `Authorization: Bearer <登录令牌>`。
- 仅在已有 `SWE_INTERNAL_TOKEN` 已配置时提供 `X-Internal-Token: Bearer <内部密钥>`。它与登录令牌不是同一种凭据；未配置时不要求新增配置。

不新增免登录白名单或绕过原认证。在禁用应用认证的环境，必须由可信内网和网关隔离承担运维访问限制。

## 先小范围预检

选择 `Body → raw → JSON`：

```json
{
  "tenant_ids": ["实际租户ID"],
  "source_ids": ["实际来源ID"],
  "agent_ids": ["default"],
  "limit": 50
}
```

各过滤项可以省略，省略表示不限制该维度；不要用空数组表示全部，空数组会被拒绝。`job_ids` 可进一步限定任务 ID。`limit` 范围为 1～200，限制本页检查的工作量而不保证恰好返回同样数量的匹配任务。

预检时应看到 `would_insert`、`would_update` 或 `unchanged`，同时检查：

- `instance_id`：本次请求命中的实例。
- `definition_scope`：只覆盖服务实际可见的文件系统。
- `memory_scope`：只覆盖当前实例已加载的内存。
- `memory_incomplete`、`counts.memory_missing` 和各项 `warnings`：是否有状态取不到。
- `items[].reason`、`differences`：身份、归属或数据冲突，只列原因/字段名，不返回完整任务内容。
- `next_cursor`：是否还需要继续读取；非空就未完成本轮扫描。

无效 JSON、坏任务或缺失内存不是空目录，也不能笼统当成全部成功。预检不写两张目标表，不创建工作区，不重新注册平台任务。

## 正式导入

将地址改为 `/import`，保持相同筛选条件，并从第一页开始：

```json
{
  "tenant_ids": ["实际租户ID"],
  "source_ids": ["实际来源ID"],
  "agent_ids": ["default"],
  "limit": 50
}
```

不要将预检最后返回的继续游标当成导入的起点，否则是在请求导入后面的页。首次导入省略 `cursor`。

得到非空 `next_cursor` 后，复制它作为下一次同接口请求的 `cursor`，其他筛选条件不变：

```json
{
  "tenant_ids": ["实际租户ID"],
  "source_ids": ["实际来源ID"],
  "agent_ids": ["default"],
  "limit": 50,
  "cursor": "上一次响应的next_cursor"
}
```

重复调用直到 `next_cursor` 为空。每页的计数都是本页结果，不是全量累计结果，需要保存各页响应。即使一页没有匹配项，只要游标非空仍需继续。

状态含义：

| 状态 | 含义 |
| --- | --- |
| `inserted` | 本次插入任务定义及初始状态 |
| `updated` | 更新本迁移器拥有的同来源旧路径快照，或补齐缺失状态行 |
| `unchanged` | 可比较的业务内容没有变化；观察水位和技术版本仍可能推进 |
| `conflict` | 归属、删除、来源或版本受到保护，没有强行覆盖 |
| `failed` | 当前项处理失败；当前任务事务回滚，其他合法项可继续 |
| `excluded` | 独立系统任务等被明确排除，不计作业务任务导入成功 |

同一任务定义与状态同事务提交，不存在“定义插入成功、状态失败却报告整体成功”。重跑同页或从头重跑不会重复创建任务，不改变旧运行行为。

同步全量扫描可以省略各维度过滤，但客户端仍需遵守游标分页；推荐使用上文异步入口由后台自动完成。只扫描当前服务挂载的用户任务文件；不是跨实例文件同步，也不会把系统配置合成为任务。

## 内存缺失与补迁

`memory_incomplete=true` 不表示定义导入失败，也不表示数据库已有状态被清空。可恢复的文件绑定、未读和摘要仍可保存；缺字段不会当成零值覆盖。

若用户的 Workspace 实际加载在其他实例，用该用户原有的路由 Header 调用接口，并在正文限定该用户及来源。网关命中相应实例后，再从第一页手工重跑补迁。

如果该 Workspace 已卸载或实例已重启，过去只存在内存中的状态可能已经不可恢复。迁移接口不会为了补状态启动 Workspace，不会把默认空对象当作过去状态，也不补跑任务。

## 导入后核对

使用同样范围调用 `/verify`，同样从第一页开始并循环 `next_cursor` 至为空。

核对结果需同时看 `matched`、`different`、`missing`、`conflict`、`failed` 及内存缺失提示，不能只看 HTTP 200 或 `partial_failure=false`。`matched` 只证明当前页实际可比较的来源字段一致，不证明未取得的内存状态也已迁完。

核对分为 `phase=source` 和 `phase=database` 两段，第二段检查已导入但可能失去来源的记录。继续用同一接口、同一过滤条件传递 `next_cursor` 即可，不要在第一段结束时停下，也不要手工修改游标前缀。`scanned_database_rows` 表示第二段本页检查的数据库记录数。

第二段若出现 `source_missing`，表示当前可见来源中没有对应完整身份，不等于已确认任务应当删除；可能是文件已变化、可见范围不同或目录问题。`source_unreadable` 表示来源目前无法读取。这些都只报告，不删除或禁用目标记录。第二段不再采集内存，该页 `memory_incomplete=false` 不能抹掉第一段已经报告的内存缺失。

来源仍可能被旧接口或执行流程修改，核对是新的观察时点，不是停机一致性切换。发现合理新变化时可以再导入一轮；不提供 force 覆盖 Scheduler 归属、已删除目标或不明来源数据的参数。

还要对比原文件、旧任务查询和平台入口不变。抽样验证一个原普通任务、一个原批任务按原通道执行，不因为迁移多产生一次执行或定时器。

## 常见诊断

- `memory_state_missing`：当前实例没有实际状态项，不作为空值覆盖依据。
- `original_cron_unknown`：没有可信的散列前排程，保留原定义并提示，不重新叠加偏移。
- `parent_identity_incomplete`：只知道父任务部分身份，不猜测其他维度。
- `batch_control_unknown`：不能确认旧批入口暂停状态，不擅自开启批入口。
- `scheduler_owned`、`target_managed`：新管理或实际执行路径已经持有数据，快照导入停止覆盖。
- `target_deleted`：不恢复已删除任务。
- `different_source`、`unowned_snapshot`：来源不同或不是本迁移器导入，需人工核对。
- `stale_snapshot`、`stale_file_version`、`stale_state_snapshot`：较新记录受保护，不倒退覆盖。
- `orphan_state`：目标只有状态、没有可信定义，不自动嫁接任务。
- `duplicate_job_identity`：同一文件存在重复任务标识，相关项均不导入，不任意选择首条或末条覆盖。
- `invalid_agent_config`：Agent 引用配置损坏、越界或存在歧义，没有猜测 Agent ID；配置缺失本身不阻止常规目录采集。
- `invalid_job`、`invalid_or_unsafe_file`：源数据或路径有问题，结合相对来源位置检查，不修改文件去“修复”。
- `409`：游标、过滤条件或文件清单/当前文件发生变化。保留已成功数据，从第一页重跑，不手工拼接游标。
- `503`：源存储、共用数据库或目标表不可用，先排查基础设施与手工建表结果；不要把它当作零任务成功。

读取上限为单个任务文件 8 MiB、单页 1～200 个检查项、每页至多 100 个文件，来源清单设有 20,000 个任务文件的保护上限。超过上限会明确报错，不静默截断。自定义工作区目录使用只读配置解析确定 Agent ID，配置映射改变会使旧游标失效；旧 `scope.v1.` 目录可读取但不会自动改名。

## 上线观察

由上线操作者在预发布先执行小范围完整预检→导入→核对，再扩大范围。观察各页失败和冲突原因、内存缺失数量、数据库错误及响应耗时；成功信号是业务字段对照通过、重复导入无重复任务、旧文件/旧表/平台注册和执行行为不变。

在网关或 SWE 访问日志中按 `/api/internal/cron/migration/` 筛选，重点看持续 `5xx`、重复 `409`、异常 `401` 和请求耗时；逐项数据质量问题以保存的响应中 `counts`、`reason`、`warnings` 为准。首次验证由上线操作者负责，建议在预发布同一验证窗口完成小范围首次导入、重跑和核对，再放大范围。

出现原任务行为变化、非预期业务表写入、目标数据被异常覆盖或持续数据库错误时，停止新提交，并对正在运行的异步任务调用 `/stop`、确认终态；仅停止 Postman 请求不会停止后台任务。预期运维写入只有上述异步进度两表。保留任务 ID、各页响应和来源基线，再回退本次应用变更。不要通过删表或回写旧文件盲目撤销。
